### 官服计价 = 新件价 − 旧件残值 + 固定工时（2026-11-12 定案）

`logs/net_capture_official.jsonl` 一单的完整证据链（电马达 `59559375…`，修火花塞
`rgm_ef_spark10021`）：

| 环节 | 观测 |
| --- | --- |
| 21/2 `hlopebmchhp.f3` | `(266, 0)` = 296 × 0.9 的旧件残值 |
| 21/2 `hpopgbjohpk.f2` | `(296, 5)` 新件价 |
| 21/4 请求 `f3` | **30** = 296 − 266，客户端按这个差价报价 |
| 实际扣费 | 银币 5000 → 4970，扣 **30** |
| 21/4 回包锁 | `RemainMin=120` = 齿轮档位 2 小时 |
| 下单后该件 | 完好度 1.0，**GUID 由 `6414fec0…` 变成 `b411a83e…`** |

三条硬结论：

1. **"修理"就是换一个同型号新件**（GUID 变、完好度 1.0），收 `新件价 − 旧件残值`；
2. **残值是品类属性，与磨损无关**。同一单四件的完好度都在 0.9999 附近，残值率却是
   轴承 324/845 = 0.383、线轴 239/624 = 0.383、摩擦片 289/754 = 0.383、齿轮 266/296 = 0.9
   —— 所以"几乎全新的件修理免费"是错的；
3. **21/4 只处理 args(503) 里列出的件**。那一单只列了齿轮，回包的 21/2 里轴承、
   摩擦片的 GUID 一个都没动。按件收费就必须按件施工。

工时（`hpopgbjohpk.f3`）是按品类的固定档位，实测：52 齿轮 2h、7 轴承 36h、
8 线轴/线杯 36h、9 摩擦制动器 24h、10 润滑油 18h；竿件 4/5/36 与本体 6 无样本，
走 `workshop_default_repair_hours`（默认 24h）。

**轮油例外，残值 0（2026-11-12 03:3x 修正）**：同一份回包里第五槽（轮油，
`f0=0edd4e21…`）的 `hlopebmchhp.f3` 是 **`(0, 0)`** —— 旧油不折抵，客户端按新件
全价报。我们原来把轮油并进轴承那档 0.383，导致 21/2 发 f3=19、客户端报全价 50，
换件的严格报价校验判不过 → 玩家点「更换」直接弹「发生内部错误」（03:28~03:29
三单，日志 `client=50 server=31`）。现走 `workshop_oil_residual_rate` = 0。

顺带把那一槽的 21 种油看全了，`f3`（工时）其实是**逐件**的：

| 油 | f2 新件价 | f3 工时 |
| --- | --- | --- |
| `syb_reel_oil` | 2706 银 + 26 金 | 18h |
| `sat_reel_oil` | 6039 + 58 | 18h |
| `blg_reel_oil`（SynthLab Balance） | **0 银 + 49 金** | **0h** |
| `m_au_reel_oil`（Mechanics Aero ultra） | **0 银 + 165 金** | **0h** |
| `msh_reel_oil` | 0 + 38 | 0h |

规律很干净：**有银币价的油 f3=18，纯金币价的油 f3=0** —— `f3` 只约束银币路径，
金币即时。所以我们这边轮油若统一按银币计价，18h 这一档是自洽的；哪天把油价
改成官服那种金币计价，必须跟着把工时可成按件取值。

我们侧的落地：`src/internal/gameserver/workshop_official_price.go` 是唯一口径来源，
残值率/工时都走 tunable（`workshop_wear_part_residual_rate` = 0.383、
`workshop_gear_residual_rate` = 0.9、`workshop_durable_residual_rate` = 0.9、
`workshop_oil_residual_rate` = 0、`workshop_default_repair_hours` = 24）。测试用
`workshopPageSilver()` 把契约钉成"下单收的钱 == 界面写的钱"，而不是钉死某个数字。

**旧口径为什么错**：`hlopebmchhp.f3` 原来发的是 `round(磨损×500)` 的"修理费"，
客户端把它当成"0 折抵" → 界面算全价、我们只收几银。实测对不上的两单：
界面 2197 / 实扣 3（`spin_10036_S98H`）、界面 3756 / 实扣 62（`spin_5825`）。
纯换件的单子反而一直是对的（977/977、2398/2398、21134/21134、600/600），
因为那条路径本来就走 `partPrice`。**混合单必崩**，因为同型号件被当成"免费修"。

  不符合任何单一比例。我们目前发 `price/10`（历史猜测）。它不参与计费（扣费只用
  `f2 − f3`），所以先不动，等抓到能对照界面的样本再定。

- `hlopebmchhp.f3` 的**金币列**：三件样本是 0 / 2 / 2（新件金币价 5 / 8 / 7），

## `21/3` 是选中预览、`21/4` 才是下单（2026-11-12 01:0x 定案）

把 `logs/gameserver.log` 里全部 107 帧工坊请求逐帧解码后，客户端的真实节奏是：

```
23:07:52  21/3  826e09da  n=1  cat=36                    勾竿坯
23:07:53  21/3  826e09da  n=2  cat=36,4                  再勾手柄
23:07:54  21/3  826e09da  n=3  cat=36,4,5                再勾导环
23:07:55  21/4  826e09da  n=3  cost=2176                 ← 点「修理」才下单
```

- **每勾选/取消一个部位就重发一帧 `21/3`，条目是累积的**（`n=1 → 2 → 3`）；
  取消同理：16:01:22→32 连发 `n=1,2,3,4` 又回到 `3,2,1`，整段一次 `21/4` 都没有。
- `21/3` 的 `f3` 恒为 0（客户端还没有价），`21/4` 才回填整张单的总价。
- 所以 `21/4` 是「修理」按钮，`21/3` 只是界面在同步选中状态。

**我们原来把 `21/3` 当成交**，后果是：第一帧就入队扣费，后面几帧全部撞在办任务
分支被当成幂等重放**吞掉**。实测 23:07 那单——玩家勾了 3 个部位、界面写着 2176 银，
服务端只修了竿坯、只扣了 8 银。同类吞单在 22:53、00:49、00:51、01:06 各出现一次。

落地（`econ_market.go`）：

| 帧 | handler | 行为 |
| --- | --- | --- |
| `21/3` | `hWorkshopQuote` | 只回当前物品树。不改耐久、不扣费、不登记任务、不推 `4/22`；已在工坊的物品照样带时效对象（`ItemToTree` 从任务表投影） |
| `21/4` | `hWorkshopOrder` | 唯一下单入口。按整张单一次算清、一次扣费、一次入队 |

### 结算口径：按界面报价收，只用「新件全价」封顶（2026-11-12 03:4x 定案）

历史遗留：客户端给"同型号部位"报的价来自 `21/2` 里那条同型号工单的 `f2`，而我们
发的是换件价（`partAlternatives` 用 `partPrice`：竿坯 1200 来自 `partBasePrice[36]`，
齿轮 2496 来自 `480 × 传动比`），客户端再自己减掉旧件折抵；我们按
`round(磨损 × 500)` 收。两个口径差几个数量级：

| 物品 | 我们发的 `f2` | 客户端 `21/4` 报价 | 旧口径实收 |
| --- | --- | --- | --- |
| 齿轮 `rgm_ef_lagoon-hp4000s_10024`(52) | 2496 | **2472** | 24 |
| 竿坯 `rodblank_syb_fortuna_s68mh`(36) | 1200 | **1200** | 0 |

早期靠严格比对（`workshopQuoteMatches`，容差 `max(1, server/20)`）+ 分段兜底来
硬扛，结果是玩家侧连爆两种「发生内部错误」：

| 现场 | 玩家操作 | client | server | 旧实现日志 / 结果 |
| --- | --- | --- | --- | --- |
| 2026-11-12 03:12:56 | 同时勾「修理一个件 + 更换另一个件」 | 2046 | 550 | 「客户端报价异常」→ 拒单 |
| 2026-11-12 03:34:17 | 只换件 | 565 | 742 | 「客户端报价异常」→ 拒单 |
| 2026-11-12 03:43:17 | 换一件比旧件便宜的新件 | 100 | 259 | 「客户端报价低于服务端」→ 拒单 |

三条现场同一个根因：**换件分支的残值取错了件**。客户端算
`Σ(新件价 f2 − 该槽位旧件残值 f3)`，`f3` 是 `21/2` 按**槽位**发下去的、与"换成哪
一件"无关；旧实现拿**新件**价再折一次残值，同型号换（官服抓包那一单）两者相等所以
没暴露，换型号时必然错。旧件比新件贵 → 客户端差额比我们小甚至为负 → 判压价拒单。
`03:12:56` 那一单 12 秒后只勾一个件就过了，印证混单报错是同源。

现在 `hWorkshopOrder` 的口径（`econ_market.go`）：

1. 换件残值取**旧件**（替换 `fields[idx].Val` 之前抓住 `oldChild`，用它的
   `childNumericID` 走 `partRepairBasePrice`，与 `21/2` 发 `f3` 同一条链路）；
2. 旧件残值 > 新件价 → 差额按 **0** 收（以旧换新不退差价），并置 `swapCovered`，
   否则会被零金额判定当成价格表缺口拒掉；
3. 结算以客户端报价为准，只有两种情况用服务端估价：**同一件被列了多次**
   （`len(orders) > len(seenOrderCat)`）和**报价超过新件全价**；
4. 两边差异 > 20% 只打 WARN 观测，不再拒单。

| 情况 | 处理 | 日志 |
| --- | --- | --- |
| 同一件被列多次 | 按去重后的服务端估价收 | INFO |
| `client > 新件全价` | 按服务端估价收 | WARN |
| `client` 与估价差 > 20% | **仍按界面报价收** | WARN（仅观测） |
| 其余（含 `client < server`） | 按界面报价收 | — |

零金额判定放在结算**之后**，`costSilver <= 0` 时三种：纯修理算出 0（磨损不足一个
计费单位）放行、`partSwapped && swapCovered`（旧件抵掉新件）放行、其余（新件没标价）
拒单。

代价（明确记录）：服务端不再校验"报价是否偏低"，改过的客户端可以少付。换来的是
任何组合都不再报错、界面与实扣一致。要恢复严格校验，得先把配件价表校准到官方口径
（见 docs 的 26 条官方报价样本）。

> 待办：`21/2` 那条同型号工单的 `f2` 报换件价，界面显示的就是这个数（修一根
> 竿坯玩家看到 1200、实际收 0）。要彻底对齐，得让同型号工单的 `f2` 等于我们
> 真正会收的修理价——需要先做一次实机实验确认客户端是否对 `f2` 再做减法。

## 配件价从哪来：库里有值优先，库里没有走兜底（2026-11-12 定案）

玩家定的口径只有一条：**数据库里有值就优先用库里的值，库里没有就走兜底，
任何一层缺失都不许让报价失败**。落到代码里是一条链（
`internal/gameserver/workshop_part_price.go` + `repair_part_mult.go`）：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `workshop_part_price`（该图精确行） | 运营为「这张图的这个件」写死的价 |
| 2 | `workshop_part_price`（`map_key=''` 全局行） | 运营为「这个件」写死的价 |
| 3 | `item_price` 静态价 | 静态资料表，seed 刷新会整表替换 |
| 4 | 属性推导 | 摩擦片 26×kg²、齿轮 480×传动比、轴承 品质×10、线杯 容量×12、轮油 50 银 |
| 5 | `partBasePrice[品类]` | 代码内置的品类基准价 |
| 6 | 500 银兜底 | 连品类都查不到时的保命值 |

1、2 命中就**原样使用，不再乘部位维修倍率**——运营把价写死了，再乘一次就不是
他填的数。要按图定价就再写一行 `map_key` 精确行，两行并存时精确行优先。

### `workshop_part_price`（迁移 9100010）

```sql
item_id TEXT, map_key TEXT DEFAULT '',   -- map_key='' = 全局
silver INTEGER, gold INTEGER, hours INTEGER,  -- 三列都可空
source TEXT, note TEXT, updated_at REAL,
PRIMARY KEY(item_id, map_key)
```

**NULL 与 0 的区别是这张表的关键**：NULL = 这一列不覆盖（继续往下一层掉），
0 = 真的按 0 收。官服轮油那种「0 银 + 49 金 + 0 小时（即时）」必须靠这个区别
才能表达出来。只覆盖银币时金币按 `银/110` 重算，保住既有汇率；两列都写就原样用。

为什么不并进 `item_price`：它登记在 `store.StaticTables` 里，seed 刷新会整表
替换，后台手改的价格下次刷新就没了（`species_value_rates`、`shop_item_override`
都是同一个理由独立出来的）。

### 工时也走这张表

`21/2` 的 `hpopgbjohpk.f3` 和银币队列的锁时长是同一个值，现在都取
`workshopPartHoursFor(mapKey, itemID, cat)`：覆盖行有 `hours` 就用它（**0 = 即时**），
整列都没有值才回落到品类默认。取值跨行——该图精确行只写了价格没写工时时，
全局行的工时仍然有效（`store.WorkshopPartHours` 专门为这个跨行 CASE 写的）。

银币排队路径仍会兜一层 `jobHours < 1 → 1`：工时 0 的件走银币排队没有意义，
玩家选银币就是接受等待；金币路径本来就即时，不受影响。

### 后台入口

| 方法 | 路径 | 说明 |

| `GET` | `/api/workshop/part_prices?item_id=` | 列覆盖行，附带配件中文名与品类 |

理由：21/2 一次面板打开约几十次单行主键查询，本地 SQLite 亚毫秒级；而进程级
快照会引入"后台改完价玩家还看不到"，`species_value_rates` 已经踩过一次）。

  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \

## 银币修理要等、金币即时

官方用户手册（rf4game.com/userguide，工作坊一节）原文：

> Click the button with silver coins to hand over the object to be repaired.
> **The item remains in the workshop for the whole repair period.** …
> If you select repair for silver and leave an item in the workshop,
> **you will need to pick it up yourself when repair is complete.**

即银币修理期间物品**离开背包、留在工坊**，修好自己取回；金币修理立即完成。
界面上那两个角标就是上一节 `hpopgbjohpk.f3`：「N 小时」对应银币，「即时」对应金币。

我们侧的落地：容器枚举里没有"工坊"位置（`misc_fix.go`：1/6 tent、2/7 car、
3/8 boat、4/9 scooter、5 keepnet、10/11 house，其余按背包），所以"移出背包"
无法用现有字段表达，改成"扣费 → 入队 → 完工生效"的三步状态机：
`21/4` 银币分支只扣钱并把完成后的快照写进 `workshop_repair_job`，完工由
`workshopSettleRepairs` 落地（登录 / `21/1` / `21/2` / 后台 5 秒扫描四处触发）。
实现见 `src/internal/gameserver/workshop_repair_queue.go`。

### 计时按"在线时长"，下线冻结（2026-11-11 实机口径）

玩家口述的官服表现：物件进工坊后带一把锁 + 倒计时，**只有在线时倒计时才走**，
下线就冻住；修好之后要打开工坊才会显示取回。

所以库里存两列（迁移 `9100008_workshop_repair_online_clock.sql`）：

| 列 | 含义 |
| --- | --- |
| `remaining_s` | 还欠多少秒**在线**工时，唯一判定依据 |
| `tick_ts` | 上一次扣减的时刻，`now - tick_ts` 就是这一拍该扣多少 |
| `due_ts` | 仅展示用投影（`tick_ts + remaining_s`），不参与判定 |

- 后台 5 秒扫描只给 `OnlineUIDs()` 里的玩家扣时（`TickWorkshopRepairJobs`），
  离线玩家的 `remaining_s` 不会变，扫他们只会误扣；
- 登录时 `ResetWorkshopRepairTick` 把 `tick_ts` 拨到当前、**不补扣**离线段，
  代价是掉线到重登之间最后不到 5 秒的在线时长会丢，这正是冻结语义；
- 打开工坊（`21/1`/`21/2`）也会先补扣一次，否则倒计时永远差一个扫描周期。

**工时不再按磨损折算**（2026-11-12 更正）：官服给的是品类固定档位（见
"官服计价"一节），所以"满磨损 = 6 小时、10% ≈ 1 小时"那套折算和它的 tunable
`workshop_silver_repair_hours` 一起删掉了。现在一单多件时取**订单里列出的件**
中最长的一档；旧实现会遍历全部内件，导致"只修齿轮却要等轴承的 36 小时"。

注意工时是**游戏内小时**、并且计时只算**在线时长**（下线冻结，见上）。
最长的 36 档折现实是 1.5 小时，正常玩一局就过去了；嫌长就直接改
`workshop_official_price.go` 里 `workshopPartHoursByCat` 那张表，别去动
`workshopRepairSeconds` 的换算系数（那个系数跟世界时钟绑定）。

已知偏差：
1. 等待期间物品仍在背包、耐久未回满时仍可使用（官服是背包里同件物品**带锁置灰**，
   工坊面板显示剩余时间；见下节实测，物品本身确实还在背包里）；
2. 在办期间 `21/2` **照常报价**。曾经试过"没报价就没入口"来防重复下单，
   实机翻车：回空 `args(143)` 会让客户端把整个面板画白（零件行、价格、换件列表
   全没），玩家看到的是"修理选项都没有了"。挡重复下单由 `21/4` 的幂等分支负责。

### `4/22` 的到达时机：必须延迟，不能贴着回包发（2026-11-12 实机 A/B）

这条推送**不是**可以省的重复刷新，它是进 `kItemState_Repairing` 的唯一通道——
`21/3`/`21/4` 的响应树本身改不动面板（客户端按 `csCreated` 版本戳判断，回包里
我们投影的新戳只保证"不被丢弃"，真正切状态的是随后那条 `4/22`）。但它也**不能
紧跟在回包后面**，否则客户端当场弹「发生内部错误」（通用兜底
`kCommon_E_INTERNAL`，不写 `Player.log`、不带错误码，非常难定位）。

三组实机对照（同一次银币换件，只改下发行为）：

| 下发行为 | 弹错 | 角标/倒计时 |
| --- | --- | --- |
| 贴回包同步发（0ms，同一 goroutine） | **弹「发生内部错误」** | 立刻变「修理中 + 倒计时」 |
| 完全不发（`workshop_order_push422=0`） | 不弹 | **没有**，要退出重连（走 `4/5` 全量背包）才变「修理中」 |
| 延迟发（默认 2500ms） | **待实机确认**（2026-11-12 00:25 已部署） | 预期与第一行相同 |

官服自己的节奏也是延迟的（`logs/net_capture_official.jsonl`，毫秒差按 s2c 序号回算）：

| s2c seq | 帧 | 相对时刻 |
| --- | --- | --- |
| 334 | `21/3` 回包 call=399 | — |
| 335 | `2/1` 玩家资料推送 | +2103ms |
| （c2s） | 客户端发 `21/4` call=400（金币支付确认） | 落在 336 之前 |
| 336 | `21/4` 回包 call=400 | +1287ms |
| 337 | **`4/22`** call=202 | **+591ms（距 `21/3` 回包 4004ms）** |
| 338 | `21/3` 回包 call=401（第二单） | +36ms |

也就是说官服那条 `4/22` 从来不是同一毫秒：`21/3` 回包之后先有一次 `2/1`，再有一次
完整的 `21/4` 往返，`4/22` 才到。

同一段抓包里还暴露了官服自己的一个不对称，**别照着抄**：

| 帧 | 时效对象 | 物品版本戳 `csCreated` |
| --- | --- | --- |
| `21/3←` call=399 | **null** | `…463103480` |
| `21/4←` call=400 | `{workshop_01,1,597,120}` | `…507057829` |

| `21/3←` call=401 | 同上 | `…514974643` |

即：**创建这个任务的那次 `21/3` 回包里并没有锁**（官服是回包之后才把任务落成"可见"），
锁是靠随后那条 `4/22` 才进客户端的。

### 版本戳（`csCreated`）必须逐帧递增：不能持平，更不能回退（2026-11-12 01:31 定案）

客户端按物品树里的版本戳决定要不要采纳一次下发：**戳没有严格变大就整包丢弃**，
连 `f24` 那个时效对象一起丢（渔轮是 `dgjinoebdop.f21`，竿是 `cnolibojkao` 的对应格，
统一用 `csnames.go` 的 `csCreated` 定位，别写死下标）。所以"进修理中"要求的不只是
"发一条带锁的 `4/22`"，而是**这条推送的戳必须比此前所有下发都大**。

01:31 那单（`guid=14deab68`，parts=3，silver=1006）四帧的实测：

| 时刻 | 帧 | `csCreated` | 时效对象 |
| --- | --- | --- | --- |
| 01:31:22.099 | `21/3` 回包（勾选预览） | `…462105`（item 行原值） | null |
| 01:31:23.006 | `21/4` 回包（下单） | `…955954`（bump 后） | null（我们摘掉了） |
| 01:31:23.011 | `21/3` 回包（下完单客户端又发一帧） | **`…462105` 回退** | 有 |
| 01:31:25.506 | `4/22` 推送（延迟 2500ms） | **`…955954`，与下单回包同值** | 有 |

客户端在 01:31:23 已经从 `21/4` 回包见过 `…955954`，于是 2.5 秒后那条 `4/22` 被判旧
丢弃 → 面板一直停在"修好了"，**退出重连**（走 `4/5` 全量背包、不参与版本比较）才变成
"修理中"。玩家原话：「现在换多个不会报错了，但是需要重连才会进入维修中」。

官服同一条链路则是帧帧递增，从不持平：`s2c#334` `…463103480` → `#336` `…507057829`
→ `#337` `…507058188` → `#338` `…514974643`。

修法（`stampWorkshopTree` / `bumpWorkshopCreated`，进程内序号发放）：

- `21/3` 预览回包也抬戳，不再直接回 item 行的旧值；
- `21/4` 回包用的戳、任务快照里的戳、幂等重放回包的戳，统一由同一条通道发放；
- `4/22` 在**真正发出去的那一刻**再抬一次——它是延迟 2500ms 发的，这中间客户端还会
  拿到预览回包与诊断回包，沿用下单那刻的戳必然打平甚至更小。

为什么不能只靠 `netTicksNow()`：一次交互里同一件东西要下发三四回，间隔可以短到微秒，
实测两次 `netTicksNow()` 会返回**完全相同**的值（`workshop_order_push_delay_ms=0` 的
测试与回滚场景尤其容易撞上）。所以版本戳由 `workshopStampSeq`（`atomic.Uint64`）发放，
保证"发放顺序 = 戳的大小顺序"，不再依赖时钟粒度与延迟。

回归用例：`TestWorkshopVersionStampStrictlyIncreases`（预览 < 下单回包 < 下单后的预览
< `4/22`），以及 `TestReelPartSnapshot*` 里"推送与回包除版本戳外必须一致、且推送的戳更大"。

**我们原来两边都带，2026-11-12 00:45 实机证明是伤的**，不是"多给一次不伤"：

| 帧 | 官服 | 我们（旧） | 我们（2026-11-12 00:40 之后） |
| --- | --- | --- | --- |
| `21/3`（勾选预览，下单前） | 无锁 | 带锁 | **无锁，且不再改任何状态** |
| `21/3`（下完单客户端又发的那帧） | 有锁 | 带锁 | 有锁（任务已在办，`ItemToTree` 从任务表投影） |
| `21/4←`（下单回包） | 带锁 | 带锁 | **无锁**（树没变，见下） |
| `4/22`（推送） | 带锁 | 带锁 | 带锁 |

证据（`logs/gameserver.log` + 客户端 `Player.log`）：

- 00:45:53 修一根耐久 0.9992 的竿 → 回包 605B **带锁** → 客户端当场弹
  「发生内部错误」，**而且没有下发 21/4**（本该在 +1.19 秒补上的支付确认帧没来，
  下一步直接跳到 `17/4` 拆卸）；
- 00:46:52 换摩擦片 → 回包同样带锁，却照常补了 `21/4`，且 `f3=1463`
  **正好等于服务端扣的钱**。

两者的差别是"回包里这件东西有没有真的变"：换件换上去一只新型号，树变了；
同型号修理排的是队，回包内容和下单前**一模一样**，再叠一把"已经在修"的锁就
自相矛盾。所以回包摘锁，状态只从 `4/22` 进。

摘锁之后 A/B 干净：00:28:21 同一次银币换件（摘锁前）客户端 8 秒内连发 3 次
`21/3`、一次 `21/4` 都没有；01:01:38（摘锁后）当场在 01:01:40 拿到 `21/4`。

> **`21/4` 的 `f3` 是"要付多少"，不是"客户端乱报的费用"。**
> 实测同一单：`21/3` 的 `f3=0`，`21/4` 的 `f3=1463`（= 服务端扣的银币数）。
> 之前记的"银币那次 f3=0、金币那次 f3=30"其实是把 `21/3` 与 `21/4` 两帧当成
> 同一类请求对比出来的错觉——`21/3` 永远是 0，价格在 `21/4` 里回填。

实现：回包一律走 `workshopOrderReplyBytes`（`workshop_repair_lock.go`），
它在**副本**上摘锁，入参那棵树原样留给 `4/22` 推送，绝不同一棵树发两次不同内容。
紧急回滚：`tunables.workshop_order_reply_lock = 1` 恢复"回包也带锁"的旧行为。

如果摘锁后仍弹错，下一步就是按官服这个形状继续退回"回包连版本戳都不抬"
（官服 `21/3←` 的 `csCreated` 是旧值，`21/4←` 才抬）。

落地口径：下单路径一律走 `scheduleWorkshopItemPush`（`workshop_repair_lock.go`），
**不要直接调 `pushWorkshopItem`**。延迟由 `tunables.workshop_order_push_delay_ms`
控制（默认 `2500`，`<=0` 表示同步发，测试用）。到期落地那条 `4/22`
（`notifyWorkshopRepairsSettled`）不在回包回调里，保持立即发。
紧急回滚：`tunables.workshop_order_push422 = 0` 可关掉下单路径的这条推送
（代价是退回"要重连才有倒计时"）。

### 扣了钱就必须当场推 `2/1` 档案，否则玩家要重登才看到扣款（2026-11-12 02:1x 定案）

`21/4` 扣费是在服务端事务里原子完成的（`applyWalletTx`），但**客户端显示的银币/金币
是它自己缓存的档案**，服务端不推就永远不会变。玩家原话是「没有立即扣钱，是我重新
登录后才被扣钱了」——重登会重新拉一次档案，所以看起来像「重登才扣」。

官服同一单的 s2c 序列（`logs/nc.jsonl`）：

| seq | 帧 | 内容 |
| --- | --- | --- |
| 333 | `2/1`（call=200） | 档案，`ghfbofgdflm.f7`（银币）= **5000** |
| 334 | `21/3←` | 选中预览，f24 = null |
| 335 | `2/1`（call=201） | 档案，`f7` = **4970** —— 差 30 正是这一单修理费 |
| 336 | `21/4←` | 下单回包，f24 带锁 |
| 337 | `4/22` | 物品刷新 |

即：**`2/1` 在 `21/4` 回包之前发**，而且每次工坊交互都会带一条。

落地：`hWorkshopOrder` 的两条分支（银币排队 / 金币即时）都在 `return bodyOut` 之前
调 `ctx.Sess.Push2_1()`，顺序与官服一致（先 `2/1` 后回包，`4/22` 仍旧延后）。
回归用例见 `reel_part_snapshot_test.go` 的 `expectProfilePush`：下单后第一条推送必须
是 `2/1`，否则直接失败。

教训：工坊这条链上「服务端改了状态」和「客户端看得见」是两件事，凡是扣费/改余额都
要显式推档案。`Push2_1()` 在商店、卖鱼、钱包、卡片、邮件等 20 处都调了，工坊当初漏了。

### f2/f3 的定案：靠下发字节逐帧回溯对出来的

2026-11-11 一晚的每一帧下发都记在 `logs/gameserver.log` 的 `TRACE 回/推` 里（带完整
hex），把 `21/3`/`21/4` 响应里 `level_004_workshop` 后面 9 个字节读出来，和玩家当时的
实机截图并排一比，三种口径的差别一目了然：

| 时段 | f2 | f3 | 玩家看到 |
| --- | --- | --- | --- |
| 21:31–21:52 | unix 分钟 `29906731` | 剩余**现实**分钟 `60` | 角标 `00:00`，物品"秒修好/秒换件" |
| 22:08–22:13 | 世界游戏分钟 `142407567` | 剩余**游戏**分钟 `1440→1320` | **`13:05` / `19:40` / `20:24`，正常倒数** |
| 22:43 | int32 上限 `2147483647` | 剩余游戏分钟 `1440` | 角标 `00:00` |

结论：**f2 必须是"贴着客户端世界时钟 W 的起算点"，f3 必须是游戏分钟时长。**
unix 分钟（2990 万）远小于 W（1.42 亿），算出来是负数——一个负数剩余同时解释了两个
症状：角标 `00:00`，且客户端认为已经到期（"秒修好"），而状态位没人去摘
（"`00:00` 但一直显示正在维修"）。int32 上限也不是"更远的未来"，它比 W 大太多，
剩余溢出成垃圾，角标照样 `00:00`。

**不要改 wire 类型。** 曾按字段注解 `iingicaldbk = 到期/租用结束时间（FILETIME）`
把 `f2` 改成 U64 FILETIME（现在 + 剩余工时），同时改了 `wire_spec.json` 与
`tables.go`：

> 客户端**当场崩**——登录卡在"正在载入个人资料"，会话每 500ms 建一次、推完 `2/2`
> 就断，sid 连续重启；把二进制换回上一版立刻恢复。

说明客户端对这一格的 reader 是**定长 32 位**，不看 op tag。同名同义的物品本体
`f22`（`iingicaldbk`）实测确实是 64 位 FILETIME `134388726463103228`，但那是
**另一个字段**，别被注解带跑。

官服抓包那组 `{f0="workshop_01", f1=1, f2=597, f3=120}` 与本口径不符（`597` 不可能是
世界游戏分钟），大概率是解码时该对象结构错位读出的残值——以我们自己客户端上验证过的
组合为准。


回滚开关：`tunables.workshop_silver_repair_delay = 0` 可秒级退回"付钱立即修好"，
已在办的任务仍会照原剩余工时落地，不会吞钱。

## 零金额：纯修理要放行，换件要拒绝（2026-11-12 00:27 定案）

计价是 `round((1-耐久)*500)`，所以**磨损不足 1 个计费单位时折出来就是 0**：
耐久 `0.9992` → `round(0.4) = 0`。这是合法的"几乎全新的装备免费修"，
客户端自己算的报价也是 `f3=0`。

旧代码有一条"拒绝零金额交易"的守卫，本意是挡住 `item_price` 缺标价的换件
（放行等于白送一件新件），但它不区分两种情况，把纯修理一起拒了：

```
WARN "工坊换件：银币价格为 0，拒绝零金额交易" item=a1db7046
TRACE 回(兜底) cmd=21/3 kind=args len=7        ← 空 args
```

客户端收到空 args 就是「发生内部错误」（`kCommon_E_INTERNAL`）。玩家实机：一根
`0.9992` 的竿、什么都没拆、点「修理」→ 弹错、且修理根本没开始。

三种"算出 0 银币"必须分开处理：

| 情形 | `didWork` | `partSwapped` | 处理 |
| --- | --- | --- | --- |
| 客户端重放一条已完成的修理（件本来就是满的） | false | false | **幂等成功**，回当前树（`replayWorkshopItem`） |
| 纯修理，磨损不足 1 个计费单位 | true | false | **0 元成交**，照常入队 |
| 换件，新件在 `item_price` 里没标价 | true | **true** | **拒绝**（价格表缺口，不能白送） |

判据是 `partSwapped`（这次请求里有没有装上去一个新型号），在 `econ_market.go`
的换件分支末尾置位。守卫写成 `if didWork && !partSwapped { 放行 } else { 拒绝 }`。

**竿的"本体"是竿坯那一格，不是竿自己的品类 3。** 客户端点「修理」时发的条目是
`{BYTE 36, STR "rodblank_xxx"}`（`item_def` 里 `rodblank_*` 全是 36），走的是
"按品类找子件"的分支，`o.Cat == gearCatReel` 那条本体判定只覆盖轮子。所以判
"整机保养"不能只认轮：竿坯命中同型号修理分支后会 `continue`，`allRepairs` 保持
true → `wholeItemRepair` 为真 → 本体耐久随竿坯一起置 1.0，这是对的（竿的本体
耐久就是竿坯那一格的投影）。常量见 `gear_physics.go` 的 `rodCatBlank`。

**金币侧不动。** `useGold && hasRepair` 在计价之前就直接拒（同型号修理只走银币），
这是既有口径，与零金额无关。所以修本体**别点金币按钮**，那不是这条守卫的问题。
