# 四类钓法状态门与路亚线杯状态排查

> 排查日期：2026-11-12
>
> 范围：浮钓、底钓、路亚、海钓的 14/7 状态门、发鱼定时器、收线状态和线杯开关行为。
>
> 关联文档：[浮钓顺水漂流不发鱼排查](analysis-float-drift-fish-spawn-2026-11-12.md)

## 总结

四类钓法共用一条核心发鱼门：

```text
14/2 抛竿
  → scheduleBite 设置定时器
  → 定时器到点检查 CastActive / InWater
  → InWater=false 时只设置 NeedBite=true
  → InWater=true 后才进入概率、饵料、鱼种和重量判定
  → 推送 14/14
```

当前服务端把 `0x200`、`0x400`、`0x800`、`0x1000` 作为入水位。动作位 `0x40`、`0x80`、`0x2000`、`0x4000` 没有进入核心 `InWater` 掩码。

因此，四类钓法都存在同一种潜在故障：如果某种有效钓法状态只上报动作位，没有同时出现核心入水位，发鱼定时器会停在 `NeedBite=true`，服务端不会判鱼。

目前已经有实证指向的故障是浮钓顺流 `0x40`。路亚线杯不关闭时，表现也可能落入同一条状态门，但服务端没有直接接收或判断“线杯已关闭”字段。

## 共用核心门

### 定时器到点时的处理

`onRodBiteTimerTicket` 在 `InWater=false` 时直接挂起：

```go
if !st.InWater {
    st.NeedBite = true
    st.mu.Unlock()
    return
}
```

位置：`internal/gameserver/fishing.go:2169-2174`。

这一步发生后，只有后续 14/7 进入 `rigAnimInWaterMask`，服务端才会清理 `NeedBite` 并补排咬钩。

### 14/7 入水掩码

当前代码为：

```go
const rigAnimInWaterMask = 0x200 | 0x400 | 0x800 | 0x1000
```

位置：`internal/gameserver/fishing.go:300-303`。

14/7 处理器只按该掩码设置 `InWater`：

```go
if st.CastActive && !st.InWater && anim&rigAnimInWaterMask != 0 {
    st.InWater = true
    enterWater = true
    if st.NeedBite {
        st.NeedBite = false
        needBite = true
    }
}
```

位置：`internal/gameserver/handlers_game.go:1169-1179`。

## 浮钓顺流

浮钓类型定义在 `internal/gameserver/rigmeta.go:70-73`。

顺水漂流位定义为 `0x40`，位置：`internal/gameserver/fish_ecology.go:410-415`。该位只被记录到 `LureMotionMask`，没有参与核心入水判定。

如果顺流期间 14/7 持续上报 `f5=0x40`，状态会保持：

```text
CastActive = true
InWater    = false
NeedBite   = true
Pending    = nil
```

这就是“浮钓随水漂流根本不发鱼”的直接代码路径。

## 路亚线杯不关闭

### 服务端没有线杯开关字段

服务端当前只处理：

- 17/14，渔轮摩擦档位。
- 17/15，路亚收线速度档位。
- 14/7，钓组动画状态和路亚水层。
- 14/9，路亚抬竿通知，以及海钓抬竿确认。

17/15 只保存 `ReelSetting`，位置：`internal/gameserver/econ_market.go:1985-2008`。该字段用于路亚收线速度和鱼口上下文，不表示线杯开关。

服务端没有 `bail_open`、`spool_closed` 或等价状态，也没有从 14/7 其他字段解析线杯状态。

### 客户端线杯状态存在于本地状态机

客户端 `RodReelRigFishingSet` 使用 `pocnjfgklcp.hjndpplmjbd()` 查询卷线器离合/线杯状态。相关代码会根据该状态控制线杯动画、收线和张力处理。客户端还会显示 `kNotification_ReelClosed` 或 `kNotification_ReelOpened`。

逆向资料中也明确将 `hjndpplmjbd()` 标为卷线器离合/线杯状态，见 `docs/analysis-fish-fight-physics-pull-line-2026-11-07.md`。

### 为什么线杯不关时会“没有鱼”

当前服务端不直接因为“线杯开着”拒绝鱼。更可能的链路是：

1. 线杯开着时，客户端不进入有效收线或运动状态。
2. 14/7 的 `f5` 可能保持为 `0`，或者只出现没有被服务端入水掩码认可的动作位。
3. 服务端定时器到点时看到 `InWater=false`。
4. 服务端设置 `NeedBite=true` 后返回，不执行 `rollFishForRig`。
5. 只要客户端一直没有再发能命中入水掩码的状态，就不会推 14/14。

因此，“线杯不关没有鱼”与浮钓漂流问题属于同一类状态门现象，但两者的触发源不同。浮钓是明确的 `0x40` 漏判，路亚需要用实际 14/7 报文确认线杯打开时的 `f5` 序列。

## 路亚还有一个容易误判的点

路亚确实跳过了 `RigSettled` 的 12 秒守门：

```go
if !lure && !onTheDrop && now.Sub(st.CastTs) < 12*time.Second && st.TickSeen && !st.RigSettled {
    ...
}
```

位置：`internal/gameserver/fishing.go:2206-2212`。

但这只跳过“浮标或底部就位”检查，前面的 `InWater` 检查仍然生效。当前注释容易让人误以为路亚完全不需要入水状态，实际并不是这样。

## 当前风险分级

### 已确认

- 浮钓顺流 `0x40` 单独出现时不会设置 `InWater`。
- 服务端定时器到点后会永久挂起到下一次有效入水状态。
- 路亚没有服务端线杯开关状态字段。

### 高概率

- 路亚线杯打开时，客户端没有发送能命中核心入水掩码的 14/7 状态，导致同样的 `NeedBite` 卡住。
- 海钓拟饵只上报 `0x4000 Trolling` 或 `0x80 JigStep` 时，可能无法完成首次入水门。

### 待报文确认

- 底钓首个状态是否可能只有 `0x2000 MotionOnBottom` 或 `0x8 BottomTouch`。
- 路亚线杯打开时 14/7 的实际 `f5` 是 `0x0`、动作位，还是仍包含 `0x400`。
- 海钓 50-54 的拖钓和 Jig 状态是否总会叠加 `0x400` 或其他核心入水位。

## 建议的验证抓包

每类钓法各抓一杆，从 14/2 到首次 14/14，记录 14/7 的以下字段：

| 字段 | 用途 |
| --- | --- |
| `f5` | 动画位，判断是否只出现动作位而没有核心入水位 |
| `f14` | tick 序号，确认 14/7 是否仍在持续上报 |
| `f6/f7` | 速度和浮漂/竿尖运动量，区分“有 tick 但无动作”与“没有有效运动” |
| 14/3 是否出现 | 判断客户端是否已报告落水 |
| 服务端日志中的 `钓组在水中` | 判断 `InWater` 是否真正被置位 |
| 服务端日志中的 `本轮无符合条件的鱼` | 区分“已进入判鱼但权重为空”和“根本没进入判鱼” |

优先复现路亚两组对照：

1. 线杯关闭，保持收线，记录首次 `f5` 和是否出现 14/14。
2. 线杯打开，其他条件相同，记录首次 `f5`、`InWater` 和 `NeedBite`。

如果第二组日志显示 `NeedBite=true` 且没有后续“钓组在水中”，就可以确认路亚反馈与浮钓漂流属于同一个服务端状态门问题。

## 修复方向

修复不应简单把所有动画位都加入全局 `rigAnimInWaterMask`。建议按钓组类型定义入水证据：

- 浮钓允许 `0x40 StreamMoving` 作为入水证据。
- 路亚允许已确认的水中运动位作为入水证据，同时保留对 `0x0` 的拦截。
- 底钓和海钓天然饵优先保留 `0x800` 等沉底/就位位，再根据实机报文决定是否加入 `0x2000`。
- 线杯开关如果始终只存在于客户端本地，不应伪造一个服务端开关字段。服务端应根据实际 14/7 状态决定是否进入发鱼。

每个新增入水位都应有“有效状态进入判鱼”和“空中/无动作状态不判鱼”两类回归测试。

## 验证限制

本次未修改业务代码。Go 工具链在当前环境不可用，因此没有完成编译和自动化回归。路亚线杯部分已经完成服务端字段、客户端本地状态机和 14/7 发送链路的静态核对，最终是否是 `f5=0x0` 或动作位缺失仍需要一组真实 14/7 报文确认。
