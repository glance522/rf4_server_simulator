# ADR 0001：采用按风险分级的工程约束体系

Status: accepted

## Context

本项目是俄罗斯钓鱼 4 的单机服务端模拟器，20+ 位贡献者，人类与 AI Agent 混合提交，PR 分支大量带 `codex/` 前缀。

当前事实：

- 知识分散在 `README.md`、`CONTRIBUTING.md`、13 份 `docs/*.md`、`tools/` 脚本注释里，没有一份"要什么去哪找"的入口。
- 大量改动落在协议字段与结算链路上，失败模式是**静默的**：兜底空壳、契约拒绝、回执重放、客户端强转异常，都不会让服务端报错。
- PR 目前没有仓库内 Go 门禁：唯一 workflow 只在 main push 时跑 `go vet`，不跑 `go test`、不跑 `gofmt`。

同时要避免的失败模式已经很清楚：如果一上来建"完整规范大全"，文档会先于习惯死亡；如果同时引入多套流程框架，小改会被迫承担与风险不匹配的成本。

## Decision

1. **单一入口**：`CLAUDE.md` 是唯一 Agent 入口，`AGENTS.md` 只做指针，禁止两份内容。
2. **一题一主**：文档分工写进 `docs/agents/domain.md`，并明文禁止跨文档复制结论。
3. **两条路径，默认走快的**：小改直接做；只有触碰协议契约、迁移、经济结算、权限、跨包重构、新依赖、不可回滚数据变换时，才建 `specs/changes/<slug>/spec.md`（定义见 `docs/agents/workflow.md`）。
4. **红线写成 ✅/❌ 对**，每条必须能回答"怎么判定违规"，并按 L1/L2/L3 标注强制级别。
5. **门禁先建能自动跑的**：L2 CI（gofmt + build + vet + test，PR 无 paths 过滤）是主要强制层；L1 本地钩子可选；L3 靠评审与文档。
6. **能力契约从现状倒推**，只写高频陷阱，不写大全；首批四份：协议契约、钓鱼与结算、存储与幂等、工程质量。
7. **拒绝预防性过度设计**：新增任何约束前必须先回答"具体是什么事故，现有机制为什么挡不住"。

## Consequences

代价必须写清，否则这份 ADR 就是装饰：

- **文档漂移由人负责**。能力契约、spec 与代码之间不会自动同步，靠 `docs/agents/domain.md` 的对账表和评审兜底，没有机器对账工具。
- **L1 不会自动生效**。本地钩子需要每台机器自行启用，克隆后忘配就等于没有。
- **CODEOWNERS 尚未启用**。在维护者确定 GitHub 团队 handle 前，评审的强制力来自人工，不来自分支保护。
- **分级依赖判断**。Agent 需要主动判断风险等级，判断错就会让该建 spec 的改动走了快速路径。
- **增加了一次性认知成本**：改任何东西之前，先读 `CLAUDE.md` 的红线表。
- **约束工程自身的变更权受限**：红线、门禁、流程约定的改动必须走约束路径并经维护者评审，放松红线需维护者 + 相关领域核心贡献者确认，AI 只执行不修改。这套规则本身写在 `CLAUDE.md`「约束工程自身的变更」。

## Alternatives considered

- **只写一份大而全的 `CONTRIBUTING.md`**：已存在且仍在用，但它是面向人的提交规范，塞不下"协议字段怎么核对""哪些改动要建 spec"这类实现期约束，继续膨胀会变成没人读完的文档。
- **直接引入 spec-driven 工具链（多套 skill + 多套模板）**：小改的流程成本与风险不匹配，且多套入口会重复加载指令。故只保留一套目录约定（`specs/`），不引入工具。
- **不做门禁，只靠 review**：本仓库的失败模式是静默的（兜底、契约拒绝、回执重放），review 抓不到字节层面的错误，至少需要 CI 的编译与测试拦截。
