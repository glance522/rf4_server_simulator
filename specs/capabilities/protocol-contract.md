# 协议契约规范 / 高频陷阱清单

> 用法：改任何命令响应前，先看第 1 节；只读与你改动相关的段落。
> 本文只管"响应怎么发才不会被客户端打死"。命令事实表、排查步骤去 `docs/debugging-workflow.md`，不复述。

## 1. 响应形状与 args code（最高频 —— 务必先看）

- ✅ 发之前用 `.\tools\proto.ps1 <main/sub>` 拿到三样东西：响应 wire 类、每格字段的 op、数组元素的 **args code**。
  - ❌ 凭字段名或经验猜类型 → 客户端 `lpdfanjcalm<T>` 强转抛 `InvalidCastException`，**整条数据作废**，而服务端日志一切正常。
- ✅ 数组元素类型要和客户端强转目标一致；同一 wire 类在不同字段可能要求不同容器类型。
  - ❌ 该发普通 u32 数组（0x05）却发了 typed_u32arr（0x07） → 客户端整行 UI 空白（`21/1 f3` 已踩）。
- ✅ 契约校验开着跑（`internal/gameserver/contract.go` 的 `checkPushArgs`）。
  - ❌ 为了让某个响应发出去而放宽/跳过校验 → 问题从"服务端拒发"变成"客户端卡死"，更难查。

## 2. 空数组不是 null

- ✅ 列表字段没有内容时发**空数组**（对应容器 args code）。
  - ❌ 发 null → 客户端 `foreach` 崩（`21/2` 的 `poolccanfhd.f5`/507 已踩）。
- ✅ 返回结构包含玩家档案/物品等整块状态时，同样用空数组占位，不要因为"没有内容"就省掉这一格。

## 3. 兜底不是安全默认值

- ✅ 新命令先确认有没有 handler；没有就实现。
  - ❌ 依赖兜底返回空壳"先把流程跑通" → 客户端强转失败后触发看门狗/状态机回滚（上船被传回岸边），故障点与真实原因隔了三层。
- ✅ 判定"这个命令到底有没有实现"看两处：`gameserver_fallbacks_total` 指标、`TRACE 回(兜底)` 行。
  - ❌ 只看客户端现象就断定"服务端没实现"或"服务端错了"。

## 4. 改了没生效？先怀疑回执

- ✅ 用**新的 call_id**（做一次不同操作）验证改动。
  - ❌ 同一请求重发后抱怨"改了没效果"——相同回执键会重放旧响应，这是设计而非 bug。
- ✅ 需要时清表验证：`DELETE FROM request_receipts;`（先停服务）。

## 5. 客户端版本与证据

- ✅ 协议改动在 PR 里写清：客户端版本（当前基线 `4.0.25034`）、真实报文依据、回归场景。
  - ❌ "按以前的抓包改的"——没有版本与命令号的抓包不构成证据。

## 提交前快速自检

- [ ] 每个新/改响应都过了 `proto.ps1`，args code 逐格核对
- [ ] 所有列表字段都是空数组，没有 null
- [ ] 目标命令有 handler，不是靠兜底
- [ ] 契约校验没有被临时关闭或放宽
- [ ] 验证用的是新 call_id，且贴出了 trace/日志输出
- [ ] 客户端版本与回归场景写进 PR
