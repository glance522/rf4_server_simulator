# 存储、迁移与幂等规范 / 高频陷阱清单

> 用法：动表结构、写迁移、改写操作时对照。
> 只读静态库的隔离模型见 `docs/static_runtime_isolation.md`，本文不复述。

## 1. 迁移（最高频）

- ✅ 新增迁移按现有编号顺序追加：`internal/store/migrations/000NN_<slug>.sql`，并在 `schema_migrations` 落一行。
  - ❌ 修改已发布的旧迁移文件 → 老库不会重跑，新库与老库结构分叉。
- ✅ 语句必须可重复执行（`CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`、加列前判断）。
  - ❌ 裸 `CREATE TABLE` → 二次启动或回滚重跑即失败。
- ✅ 迁移要能在**旧库升级**场景跑通，不只是空库。
  - ❌ 只在全新库上验证 → 线上老档升级时炸。
- ✅ 已有做法值得照抄：用 `BEFORE INSERT ON schema_migrations` 触发器人为让迁移失败，断言失败后库仍可用（见 `internal/store/migration_cafe_campfire_test.go`、`membership_test.go`）。

## 2. 只写玩家库

- ✅ 玩家数据只写可写的玩家库；随包发布的静态配置库以只读方式挂载，只读查询。
  - ❌ 往静态库写状态 → 下次发布被覆盖，或损坏只读镜像。
- ✅ 需要"补数据"时改静态库生成流程（`cmd/seed`），而不是运行时写回去。

## 3. 幂等与事务

- ✅ 购买、退货、鱼市、邮件附件、制作、竞赛结算：一次请求一个事务，失败整体回滚。
  - ❌ 先扣钱再发货，中间出错不回滚 → 钱货不一致。
- ✅ 同一回执键（token 哈希 + main + sub + call_id）只执行一次，结果重放。
  - ❌ 在事务外更新"已处理"标记 → 并发下双执行。
- ✅ 唯一约束与完整性检查要真的存在（`internal/store/repos_integrity.go` 一类）：背包/护网容量、物品归属、重复 GUID 都要有数据库层兜底。
  - ❌ 只在 Go 代码里校验 → 并发或异常路径绕过后写坏数据。
- ⚠️ 回执是 at-least-once：业务提交后、回执完成前崩溃，重放仍可能二次副作用。发奖等关键写操作必须自身幂等，不能只靠回执。

## 4. WAL 与并发

- ✅ SQLite 开 WAL，写事务短小，避免长事务持锁。
  - ❌ 在一次事务里做网络/推送/日志 IO → 锁持有时间不可控。
- ✅ 经济事务持有期间不得再调用其它 `store.DB` 方法（单连接 SQLite 会等自身事务）；只读准备在开事务前完成。
  - ❌ 事务内再查物品定义 → 死锁或等待自身。

## 5. 测试接缝

- ✅ 存储层测试用真实 SQLite（临时库）+ 迁移，而不是 mock 掉 SQL。
  - ❌ mock 掉数据库 → 迁移与约束类问题全都测不出来。
- ✅ 迁移测试至少三条：空库跑到最新、旧版本升级到最新、迁移失败后库仍可读。

## 提交前快速自检

- [ ] 新迁移编号连续、只追加、可重复执行
- [ ] 在"旧版本库"上跑过一次升级
- [ ] 迁移失败用例存在且能证明库未被写坏
- [ ] 写操作在事务内，且幂等键正确；关键发奖自身幂等
- [ ] 没有写只读静态库
- [ ] 容量/归属/唯一性有数据库层约束兜底
