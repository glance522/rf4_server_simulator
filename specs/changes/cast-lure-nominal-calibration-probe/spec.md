# 路亚抛投名义基准标定验证（45m → 60m）

Status: done

<!-- 状态取值：draft | ready | in-progress | done | cancelled -->

## Problem Statement

玩家用 2.0m 枪柄路亚竿满力抛投时只能到约 30 米，明显低于同装备在官服的手感。
本机日志显示这不只是"数值偏低"：同一杆客户端上报的实际落点 `requested_m`
稳定在 32～33.5 米，而服务端下发的理论满力上限 `max_m` 只有 25～26 米，
`power_ratio` 长期落在 1.27 附近；换装备后两端同向变化、比值集中在 1.27～1.34。
因为抛投距离没有后台可调参数，玩家既无法自行校准，也无法判断这个 28% 的差是
标定问题还是架构问题，只能在"每次都少一截"的状态下继续玩。

## Solution

先把路亚族名义基准从 45 米抬到 60 米（与底钓族齐平），重新编译并启动，
让玩家用同一根竿、同一套线饵满力抛一杆。若实际落点随之从约 33 米抬到约 44 米，
说明客户端确实消费了服务端下发的抛距，这是一处可修的等比标定偏差；
若落点纹丝不动，则说明天花板完全由客户端决定，服务端常量无效，
应放弃在服务端继续调参，转而从客户端口径或协议层解决。

## User Stories

1. 作为玩家，我希望满力抛投距离和线饵搭配、蓄力相匹配，以便路亚玩法不至于是"够不着"的。
2. 作为排查者，我希望只改一个常量就能得到明确的二值结论，以便在动更多代码之前先确认方向。
3. 边界：非路亚钓法基准保持 60 米不变；无轮手竿与缺少装配数据时仍走旧协议基线；
   断线、炸杆、成就与资格判定仍以客户端实际上报落点为准，不因本次改动被钳制或改写。

## Implementation Decisions

- 模块：`internal/gameserver/cast_distance.go` 的 `castNominalDistanceM`，只把
  `castNominalLureM` 由 `45.0` 改为 `60.0`；`castNominalDefaultM`、`castMinPoweredM`
  与 17 个修正器一律不动。
- 测试：`cast_distance_test.go` 的 `TestCastCalibrationBands` 用名义基准比值等比缩放
  标定带上下界；这样基准回滚后期望值自动回到原区间，测试文件无需二次回滚。
  其余断言是相对大小或下限，不受影响。
- 协议：不改 14/1、14/2 任何字段形状与语义，不改 158 下发的编码方式；
  不下发新的 args code；14/2 依旧不校验、不钳制实际落点。
- 数据与迁移：不改表、不加迁移、不动静态库与任何 tunable；旧档完全兼容。
- 兼容：客户端基线仍为 4.0.25034；回滚方式为把该常量改回 `45.0` 后重新
  `build.ps1` 并重启，无需改库、无需回滚测试文件。
- 本改动按 `docs/agents/workflow.md` 的约束路径执行，因为触及下发给客户端的物理口径。

## Testing Decisions

**接缝与期望值来源**

- 单元 / 纯逻辑：`go test ./...`（含 `internal/doccheck` 仓库断言）、`go vet ./...`、
  `go build ./...`、`go run ./tools/doccheck`，本次改动后须全部重新跑一遍，
  不引用上一会话输出。`TestCastCalibrationBands` 的旧期望 28～31 / 32～36.5 米
  是手算过的既有字面量，按 `60/45` 等比换算后为 37.33～41.33 / 42.67～48.67 米；
  这是设计口径平移，不是用同一段代码重算一遍。
- 行为 / 实机一次：同一根 2.0m 枪柄竿、同一套 8g 拟饵与 0.32mm 编织线，
  补满精力饱食后连续满力抛 2～3 杆，读 `gameserver.log` 的
  「抛投距离计算」与「实际抛投请求」两行。基线来自启动段日志的实测字面量
  （`max_m` 25.0～26.3、`requested_m` 32.1～33.5）。
- 判定：`max_m` 应约 ×1.333 到 33～35 米。若 `requested_m` 同步升到 42～45 米
  → 假设成立，属标定偏差；若 `requested_m` 仍在 33 米附近 → 假设被否，应回滚常量。
- 回滚后：`TestCastCalibrationBands` 因按基准归一不会变红；绝对距离回到日志基线
  25～26 米。若未来有人把这两个区间再写成硬编码字面量，回滚就会变红，需一并改回。

## Out of Scope

- 不实现风力/风向修正、不解析客户端蓄力字段、不启用 `cast_power` 修正器
  （`castDistanceForRig` 里 `CastPower` 恒为 1 属既有半成品）。
- 不给 14/2 的 `requested_m` 加服务端上限校验或异常记录，不改变成就/资格的取值口径。
- 不调整非路亚基准、线杯档位系数、轮油效率或玩家状态系数。
- 不写 proposal / design / plan / tasks 等旁支文件。

## Further Notes

- [事实] `cast_distance.go` 头部注释写明「后续加入风力、抛投姿势、轮型或特殊技能时
  可扩展」，风力目前是明确留白，不是本次要修的内容。
- [事实] `achievements_rules.go` 记录过服务端模型与客户端实测偏差
  （实机 `requested_m=38.81` / `max_m=20.75`），并明确拒绝用模型值 clamp，
  理由是会把已验证的抛投成就误杀。
- [事实] `specs/changes/qualification-progress/spec.md` 曾因"用理论最大距离判
  抛投≥30m，短抛也算达标"改为用实际落点。
- [事实] 启动段日志里 `requested_m` 从 3.13 连续变化到 33.51，说明客户端蓄力有效，
  30 米是满力天花板而非蓄力失效。
- [推断] 换装备后两端距离同向联动（`18.88→28.73`、`26.28→33.51`、`17.16→22.93`），
  客户端很可能消费了 `158.f1` 下发的抛距。
- [假设] 客户端把 `158.f1` 当作满力抛距上限并线性缩放实际落点，因此改基准会
  等比改变手感；实机 A/B 结论见下节，假设成立。

### 实机结论（2026-11-13 22:31–22:38，同竿 A/B）

- [事实] 同一根 `b21a4a89`（2.6m / 0.5mm / spool_size=7）：改动前 `base_m=45`、
  8g、`secondary=0.704` → `max_m=17.16` / `requested_m=22.93`；改动后
  `base_m=60`、8g、`secondary=0.505` → `max_m=20.49` / `requested_m=26.28`。
  状态更差的前提下服务端仍 +19.4%、客户端 +14.6%。
- [事实] 补满状态后（`secondary` 0.464 → 0.988，其余字段逐项相同）`max_m`
  20.40 → 26.75、`requested_m` 26.82 → 32.61 / 34.93，两端同步跳变。
  按 `castPlayerStateFactor` 复算状态系数 0.7588 → 0.9946（+31.1%），
  与距离 +31.1% 完全吻合；这独立印证了玩家状态修正器的口径。
  （20.40 取自「抛投距离计算」的 `distance_m`；该次 14/2 记录的
  `max_m=23.44` 与之不同步，是两套账的既有现象，不影响本对照的其它字段。）
- [事实] 全量日志跨 11-11 / 11-13、5 根不同竿、改动前后，满力抛投的
  `requested_m / max_m` 稳定在 1.25～1.34。
- **判定：假设成立**。`158.f1` 下发的抛距参与客户端落点计算，路亚 45 米基准
  属可修的等比标定偏差，改为 60 米有效。A/B 对照须固定装备与状态：换竿（连乘系数
  约 0.56 → 0.34）叠加状态下降（0.704 → 0.464）会抵消 +33% 的基准提升。
- [事实] 饵重 3.53→18g 时服务端 `weight_factor` 仅 0.823→0.883（+7.3%），
  客户端落点 26.13→27.32（+4.5%）：`rodTestWeightFactor` 在 Test 区间内是
  对数平缓曲线，弱影响是设计而非缺陷，只有超出 Test 上限才明显衰减。
- 结论：保留 60 米基准。回滚方式见 Implementation Decisions（常量改回 `45.0` 后重新编译）。
