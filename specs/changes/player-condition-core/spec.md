## Problem Statement

四条角色状态条（精力、饱食度、舒适度、幸运/健康）在游戏里永远静止：数值在注册时写入默认值后没有任何游戏流程会再更新，进食（3/13）没有任何副作用，动作不消耗精力。玩家看不到饱食度随时间下降，精力系统名存实亡，抛投状态系数因输入恒定而恒为 1.0。迁移 00026 的注释已声明该表是"后续食物、饮料和疲劳系统共用的权威数据"，但这份权威数据没有生命周期。

## Solution

服务端成为状态条的唯一权威：饱食度按在线时间衰减，精力空闲时恢复（恢复速度受饱食度影响），抛投和搏鱼消耗精力，进食恢复饱食度，精力耗尽时以官服结果码拒绝抛投；食品/热饮消耗品提供即时恢复，篝火与天气影响舒适度，免费餐每游戏日限一次。全部变化经既有 2/2 保活与 307.f12 下发，客户端零改动；速率、消耗量与阈值全部走 tunables，可免重启标定。

## User Stories

1. 作为玩家，我希望挂机时看到饱食度条缓慢下降，以便状态条是活的。
2. 作为玩家，我希望进食后饱食度回满，并在几秒内看到条平滑回升。
3. 作为玩家，我希望抛投和搏鱼消耗精力、停竿后精力恢复，吃得越饱恢复越快；竿在水里时精力只降不升，打鱼过程里精力条是看得见往下走的。
4. 作为玩家，我希望精力耗尽时抛投被拒绝并看到"精力不足"的官服文案，而不是静默成功。
5. 边界：离线期间饱食度停扣、精力停恢复；上线从离线前的值继续（维护者决策，非官服验证口径）。
6. 边界：同一账号多会话/断线重连不产生双倍衰减或双倍消耗。
7. 边界：总开关关闭时，下发值与现状逐字段一致，抛投系数行为不变。

## Implementation Decisions

- 模块：`internal/store`（player_condition 扩列与 repo 扩展）、`internal/gameserver`（状态推进、308 构建、3/13 handler、抛投/搏鱼钩子、低精力拒绝、消耗品恢复、篝火材料、免费餐）。
- 数据与迁移：player_condition 一次扩为 4 个业务列 energy/hunger/comfort/luck_penalty（沿用 updated_ts）；迁移可重复执行、覆盖旧库升级，默认回填 0.85/0.9946/1.0/0。luck_penalty 本轮只落库与透传，不接动态（无官服数据），动态留待后续 spec。
- 计算模型：在线钟懒计算——登录/重连时冻结状态钟（只推 updated_ts，吞掉离线跨度：饱食度停扣、精力停恢复，与窝料/饮酒在线钟同一范式）；会话期间只有 2/2 环境感知读路径按 updated_ts 时间差推进，非 2/2 的 307/档案响应只读持久化值、不推进状态，避免以空环境抢走漂移区间。单次推进跨度封顶（tunable，作为会话钟停滞的安全阀），变化量超过显示噪声阈值才写回，动作引起的变更立即写回。
- 字段语义：f0=energy∈[0,energy_max]，f1=hunger∈[0,1]，f3=comfort（环境联动 + 饮用恢复），f4=luck_penalty（本轮恒 0 透传，HUD 显示 1-f4）；f2/f5/f6/f8 维持现状常量；f7 世界时钟一律真实 UTC，不动。
- 事件接入：3/13 新注册 handler（响应保持 null，与官服 resp-3-13 模板一致；幂等由通用请求回执表兜底，handler 不自带回执）。已核实：3/13 请求只携带厨房物件 ID，不携带食物实例；本服未建模食材账本，第一版只做饱食度恢复、不扣资源（食材账本接入时再补扣减与事务）。14/2 抛投做前置精力检查并扣减，精力低于阈值时以官服结果码 84 拒绝（kOperationResult_LowEnergyLevel；回包形状与既有 136 WrongRegion 拒绝共用 ReplyOperationResult 路径）；14/9 搏鱼只扣不拒（无官服拒绝样本，搏鱼中拒绝会破坏鱼战状态一致性）。
- 消耗品恢复（4/8 use 通道扩围）：品类 26 的食品/热饮进消耗品白名单，饮用/食用即时恢复状态条并与扣物同事务——咖啡→精力、茶→舒适度、可可→饱食+少量精力、其余食品→饱食度（映射依据见 Further Notes [决策]）；恢复后立即补推 2/2；总开关关闭时白名单物品维持旧行为（落回通用 handler）。酒类仍走经验加成规则不变。白名单只收可直接食用的成品（含保温瓶热饮系列），烹饪材料（面粉/糖/油/盐/调料等）不进表。tunables 读取一律在开经济事务之前完成（tunableF 装载查询有 2 秒超时，持锁事务内首次调用会超时并静默回退默认值）。
- 环境联动（舒适度）：2/2 保活拍是唯一的环境感知推进点——均衡点 = 1 − 降雨惩罚 − 寒冷惩罚（气温低于阈值）+ 篝火加成 + 晒阳加成（白昼 6:00–20:00 游戏时刻且无雨，世界钟 24 倍速），舒适度按漂移速率向均衡点靠拢；晒阳同时给精力恢复乘加成倍率。动作路径读的是上一拍持久化值，跨度 ≤ 一个保活周期，漂移误差可忽略。环境来源：会话天气计划 + 玩家位置 + 篝火到期状态；篝火加成只在玩家当前 loc/spot 与 campfire_state 一致时生效，天气或位置未知时均衡点回 1.0。
- 装备被动加成：已装配竿/轮的 item_def.attrs_json 键 `oiicogcccao`（精力恢复加成）与 `oodjilnjeen`（精力上限加成，均 0..1）求和并受 tunables 封顶，前者乘入精力恢复速率、后者加到精力上限。与物品描述加成同键，标定写入 attrs 后显示与效果同源生效；当前静态库不带这些值（官方逐条数值未采集），机制就绪、默认零效果。
- 免费餐：官服客户端无独立餐车对象，野外厨房/餐车统一走 3/13；实现为每游戏日一次免费餐（世界钟游戏日号入 kv，1 游戏日 = 1 现实小时），同日重复进食回官服结果码 16（kOperationResult_FoodAidAvailableOnceADay，客户端弹"每天限一次"文案）。
- 篝火点火材料：点燃消耗 1 木柴（woodstack）+ 1 火柴（matches）——3/11 事务内真扣，应答 f1/f2 携带扣减后的物品实例（结算基座消费）、f3 携带耗尽 GUID。已有有效篝火直接复用到期状态、不重复扣料；新点火必须两种材料同时存在，材料缺失或账务失败时整体回滚且不落篝火状态。篝火状态与材料扣减同事务提交。事务内禁止调用 ItemToTree（含嵌套写，自死锁），实例树在提交后构建。
- 篝火到期分钟时间线：802.f0 必须与 307.f13.f0 同时间线（worldTotalGameMin，世界总游戏分钟）——客户端以 307.f13.f0 校时，点燃门槛按这条线比较。会话相对线（sessionGameMinuteAt）与世界总分钟相差两千多万，永远过不了门槛（实机验证确认）。
- 推送：复用 5 秒保活节奏与 `push:profile` 契约，不新增推送频率；进食/消耗品使用成功后立即补推一次 2/2。
- 兼容：客户端基线 4.0.25034。总开关 tunable 缺省开启（与 groundbait 缺省关闭不同：本改动不触碰判鱼/经济主链路，回滚即翻开关，下发与拒绝全部旁路回现状）；表结构与旧代码可共存（多余列无写入者也无害）。
- tunables（tunables 表，30 秒缓存，改值免重启）：`player_condition_enabled`=1、`condition_hunger_decay_per_hour`=0.24、`condition_energy_regen_per_hour`=100.0、`condition_energy_max`=1.0、`condition_energy_regen_cap`=0.85、`condition_energy_regen_fishing_mult`=0、`condition_hunger_regen_floor`=0.25、`condition_cast_energy_cost`=0.01、`condition_pull_energy_cost`=0.005、`condition_low_energy_threshold`=0.05、`condition_max_backfill_hours`=12、`condition_food_hunger_restore`=0.25、`condition_coffee_energy_restore`=0.15、`condition_cocoa_hunger_restore`=0.35、`condition_cocoa_energy_restore`=0.05、`condition_tea_comfort_restore`=0.30、`condition_comfort_rain_penalty`=0.35、`condition_comfort_cold_penalty`=0.35、`condition_comfort_cold_temp_c`=5、`condition_comfort_campfire_boost`=0.5、`condition_comfort_sun_boost`=0.1、`condition_comfort_drift_per_hour`=0.5、`condition_sun_energy_regen_mult`=1.25、`condition_gear_energy_regen_cap`=0.5、`condition_gear_energy_max_cap`=0.15。除饱食衰减与精力自然恢复封顶有官服抓包锚定外均为标定值，可随时调参重标。

## Testing Decisions

- 单元（纯逻辑）：衰减/恢复推进函数用手算样例断言（饱食衰减、精力恢复 × 饱食因子 × 晒阳倍率、跨度封顶、舒适度环境均衡点漂移）；castPlayerStateFactor 删除"<=0 重置默认"分支后，0 值必须落到 0.70 下限——期望值来自手算，不得用同一份代码回算。
- 存储（真实 SQLite）：旧库（2 列）升级到 4 列的迁移可重复执行且回填正确；Ensure/Upsert 扩列后读写回环；schema_migrations 与玩家存档清单登记不变。
- 行为：进食后下一条 2/2 的 f1=1.0（对齐官服抓包观察，handler 级测试直接断言推送载荷）；同游戏日二次进食回结果码 16 且不改状态，游戏日翻天后恢复可用；离线冻结不改变状态值、只推 updated_ts（resume 单测）；抛投精力闸门低于阈值拒绝/高于阈值放行（conditionAllowsCast 单测，84 回包形状与 136 WrongRegion 共用 ReplyOperationResult 既有路径并由合同守卫把关）；动作扣减落库并保留装备精力上限加成（spendEnergy 单测）；消耗品恢复按分类落库（咖啡/茶/可可/食品各验目标条）；篝火无材料/缺任一材料整体失败且不落状态，已有篝火重复点火不重复扣料，点火扣减木柴/火柴并落库；篝火舒适度只在同一 loc/spot 生效；非 2/2 的 308 构建不推进状态；总开关关闭时读口回协议默认常量且不改库存值。
- 回滚后变红：行为组（衰减推进、进食恢复、消耗品恢复、低精力拒绝、离线冻结）回滚开关后必然变红，属预期；迁移升级与开关旁路测试应保持绿。

## Out of Scope

- f4 幸运/健康的全部动态：下降与恢复触发无任何官服样本，需先自设计规则。
  已由 `specs/changes/player-condition-health-dynamics` 接手（饥寒掉血 + 药品恢复），
  本 spec 只保留"恒 0 透传"的历史口径。
- 衣物类防寒/防热属性对舒适度均衡点的修正：模拟器未建模服装穿戴，仅在官方数据可用后接入。
- f3 舒适度的天气联动当前只用降雨/气温两个输入；云量、风力、水温对舒适度的影响留待标定时扩展。
- 进食场景的食材账本：3/13 厨房进食与 4/8 食用均不扣食材/食谱材料（官服厨房内食材状态未建模）；接入时需单独 spec 处理经济面。
- 饥饿归零后的惩罚（无数据）。
- f2/f5/f6/f8 的语义。
- 抛投状态系数的分母与 clamp 标定：`condition_energy_max` 0.85 与 clamp [0.70,1.03]
  维持（标定值）；系数构成已于 2026-11-13 由 `specs/changes/cast-skill-wiring` 改为
  精力唯一（删除 fb1d97f 的 0.55/0.45 饱食加权），本 spec 的「只修 <=0 边界」口径
  由该 change 接手。

## Further Notes

- [事实] 客户端四条状态条为纯显示组件，只做约 10 秒平滑；luck 条显示 clamp(1-f4,0,1)；客户端对 308 值无任何玩法计算，道具精力/舒适/幸运加成只出现在物品描述文案（协议基线 4.0.25034 实测）。
- [事实] 官服操作结果码 84 = 精力不足文案、16 = 免费餐每天一次文案（结果码 → 文案映射表实测）。
- [抓包] f1 约 30 秒降 0.0018~0.0020（≈0.24/现实小时），值域 [0.874,1]（n=268）；kitchen_eat 后下一条 2/2 f1=1.0；f0 静止恒 0.85，一次移动事件降 0.0086 后 15 秒内恢复。
- [决策] 精力三条口径分离（`specs/changes/energy-cap-vs-regen-cap` + 本轮）：`condition_energy_max`=1.0 是硬上限（客户端状态条按 1.0 归一化画满），`condition_energy_regen_cap`=0.85 是自然恢复的天花板（封的是"能恢复到多高"，不是"当前值不得超过"），`condition_energy_regen_fishing_mult`=0 让竿在水中时自然恢复停摆。官服一小时会话的精力是净下降的（0.85→0.83），而本仓单次抛投/拉拽只扣 0.01/0.005，垂钓时若仍按 100/h 恢复，0.36 秒就抹平一次消耗，精力条永远画满；停竿后照常快速回精力，"打完吃顿饭半分钟再战"的节奏不变。
- [推断] 0.85 为自然恢复封顶（当年按"精力上限"记，后经像素实测与官服窄带缓降修正为封顶语义）；恢复速率、动作消耗、低精力阈值、跨度封顶、消耗品恢复量、环境联动数值与漂移速率均为标定值，全部进 tunables，不作官服常量。
- [决策] 离线停扣：离线期间饱食度不衰减、精力不恢复（实现为登录/重连冻结状态钟 + 会话期推进）。维护者拍板的产品决策，非官服验证口径；若后续抓包证明官服离线衰减，再翻口径。
- [决策] 消耗品恢复映射：咖啡→精力（快）、热可可→饱食为主+少量精力、茶→舒适度（HUD 第四条"温度条"即舒适度）、其余食品→饱食度（如胡萝卜可直食）。依据为维护者实测经验 + 官方游戏提示（热茶提高舒适度），非官服数值复刻。酒类仅经验加成，与官服实机行为一致。
- [决策] 免费餐每游戏日一次：官服口径来自维护者实机确认（提示"已经用过了，一天只能用一次"，一天=游戏时间）。
- [事实] 篝火点火材料为木柴（woodstack）与火柴（matches），均为品类 42 物品（matches numid 8992、woodstack numid 16040），背包按名称检索扣减。
- [事实] 308.f8 语义定案：世界钟的绝对游戏分钟基值——客户端以 f8 分钟 + 24×真实流逝维护连续游戏钟；官服观测 0 与 -859（0xFFFFFCA5）为日修正值。802.f0（篝火到期分钟）与该时钟同线比较，因此必须与 307.f13.f0 同源（worldTotalGameMin）。
- [事实] 装备精力加成字段 `oiicogcccao`/`oodjilnjeen`（精力恢复/精力上限，0..1）为物品描述既有键；官方逐条数值在现有全部静态/抓包数据中不存在，故机制以 attrs_json 同键为数据源、默认零效果，标定即生效。
- [未验证] 官服离线是否衰减；14/2 低精力拒绝的实际服务端数值行为（形状已核实与 136 WrongRegion 同源）；食品"可食用"交互是否全部走 4/8（白名单外的物品不受影响）。
