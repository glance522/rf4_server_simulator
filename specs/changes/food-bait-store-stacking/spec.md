# 商店食物与饵料按品种合并

Status: done

## Problem Statement

玩家重复购买食物或饵料后，同一种物品会生成多个独立背包实例，界面出现重复卡片；食物与饵料同时存在时，重复实例还会挤占同一展示区域。当前购买路径为了保护可退商品，禁止了所有商品合并，但客户端本来就不允许食物和饵料退货，因此这项保护对它们没有收益。

## Solution

商店购买后，不能退货的计件物品按精确 `item_id` 并入同一容器的已有堆；食物和饵料以及不同品种之间绝不互相合并。客户端允许退货的商品继续按购买批次保留独立实例，退货行为不变。升级时还会在事务中整理旧档的重复不可退计件堆，复刻官服对存量重复项的后台合并行为。

## User Stories

1. 作为玩家，我重复购买同一种食物或饵料时，希望背包更新原有数量，而不是出现多张相同卡片。
2. 作为玩家，我希望食物和饵料始终保持不同实例，不能因为都可计件而合成同一堆。
3. 边界：客户端允许退货的商品仍按购买批次独立保存，退一件不能影响购买前已有的同类物品。
4. 边界：购买即展开的食品盒、饵料盒若只产出不可退的计件物品，也应并入对应 `item_id` 的已有堆。
5. 作为旧档玩家，我希望升级前已经重复的同品种堆在服务启动时被合并，且快捷栏、饮品增益来源等仍指向保留下来的实例。

## Approaches

- 采用：以“本次购买产出的所有实例是否允许退货”为分界；全部不可退时按现有计件规则合并并不生成无效退货凭据，否则整批保持独立。这同时覆盖散装与购买即展开的食品盒、饵料盒。
- 未采用：只给新实例分配不同的数据库槽位。它只能调整顺序，不能消除重复食物卡片。
- 未采用：所有商品重新允许合并。可退商品会与购买前库存混合，退货时无法只扣除本次购买数量。

## Implementation Decisions

- 修改 `internal/gameserver` 的商店购买入口；复用 `grantPreparedItemTx` 的同 `item_id` 合并条件，不放宽为跨品种合并。
- 购买前根据产出实例对应的物品类别判断整批是否可退；只要一件可退，整批继续独立入库并保存购买凭据。
- 全部产出均不可退时允许计件合并，并跳过客户端不会使用的退货凭据；钱包扣款、交易流水及 804 响应形状不变。
- 新增服务启动时的幂等整理：仅处理未装配、类别属于“计件且不可退”的实例，按 `uid + container + item_id` 合并；保留排序最前的 GUID，累加数量，并清除已失效的退货元数据。
- 存量整理同步重定向一条有效快捷栏绑定和饮品增益来源；同一物品若历史上占用多个快捷栏，只保留排序最前的一条，因为数据库唯一约束不允许一个 GUID 同时绑定多个槽位。
- 存量整理使用单个玩家库事务；解析失败、数量溢出或任一写入失败时整体回滚。它不写静态库、不改表结构；成功后删除重复 GUID，代码回滚不会把这些 GUID 拆回，因此部署前的玩家库备份仍是数据级回滚手段。
- 不修改命令响应类、字段、args code，不修改表结构或静态库；客户端基线仍为 `4.0.25034`。
- 新购买堆的代码回滚为恢复商店购买的独立入库策略；旧档整理的回滚边界如上。

## Testing Decisions

- 在现有商店 handler + 真实 SQLite 测试接缝新增回归测试：先放入食物和饵料，再分别重复购买，断言每个 `item_id` 只有一行、数量为手算总和，且两类 GUID 不同。
- 覆盖购买即展开的食品盒与饵料盒：连续购买后断言内容物仍只有一个同 `item_id` 堆，数量为两盒之和。
- 保留并运行退货测试，证明允许退货的类别仍产生不同 GUID，逐笔退货不会改动购买前的同类堆。
- 新增存量整理测试：同玩家、同容器、同 `item_id` 合并；不同品种、不同容器、已装配实例互不合并；快捷栏和饮品来源重定向到保留 GUID；重复执行不再改变数据。
- 用 SQLite 触发器注入删除失败，断言数量、GUID、快捷栏与退货元数据全部回滚。
- 回滚生产改动后，食物/饵料重复购买测试会因行数大于 1 而变红。
- 完成相关回归测试、`go vet ./...` 和 `go build ./...`；全仓测试中的既有偶发失败按下方 Verification 如实记录。

## Out of Scope

- 不改变食物、饵料的消耗数量、挂饵、饱食度或状态恢复逻辑。
- 不改变可退类别白名单、退货时限、价格、库存或购买幂等机制。
- 不调整背包客户端布局或数据库槽位模型。
