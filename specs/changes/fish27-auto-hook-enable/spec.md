# 保持行为 105 自动上钩概率校准

Status: done

## Problem Statement

本地实机曾观察到：服务器下发 14/14 后，静置钓组可能较长时间没有自动上钩，
开始收线或抬杆后却很快进入 14/11。此前把 27.f19 固定为 1，错误地把这一现象
归因于“自动上钩启用位未开启”。

## Conclusion

- 客户端 4.0.25034 把 27.f19 当作行为 105 的概率门控：`<= 0` 失败、`>= 1`
  恒定成功，其余值按随机数抽样；它不是布尔启用位。
- 现有 35 条官方 14/14 样本的 f19 最大值约为 0.0068。原鱼种/重量公式与样本
  量级吻合，不能用字面量 1 替换。
- 27.f21 的正式曲线池仍包含正权重、正时长的行为 105 候选，服务端没有删掉该行为。
- 原概率校准版本的本地日志也记录到无需 14/9 的自动中鱼：2026-11-10
  14:47:23 下发 14/14，14:47:42 收到 14/11，首次 14/9 直到 14:48:58 才出现。
  因此“静止分支从未触发”与现有证据不符。
- 收线或抬杆会进入客户端另一条上钩判定路径。动作后立即中鱼不能证明静止调度失效；
  它与静止行为 105 的低概率抽样可以同时成立。

## Implementation Decisions

- 保留 `internal/gameserver` 中按鱼种、重量计算 27.f19 的原校准公式和未知鱼回退表。
- 不改变 27.f21 行为候选、发鱼、饵料匹配、鱼档位、嘬饵、跑鱼和结算逻辑。
- 不在服务端伪造 14/11，也不通过提高全局概率改变玩法结果。
- 客户端版本基线为 4.0.25034。

## Testing Decisions

- 用官方样本对应的鱼种和重量锁定 f19 的概率区间，并覆盖未知鱼回退路径。
- 单独验证 27.f21 中存在可被调度的行为 105 候选，避免把“候选缺失”误判成概率问题。
- 客户端最终是否抽中属于随机运行行为，不能用服务端单元测试断言每尾鱼必定自动上钩。

## Out of Scope

- 没有新抓包或客户端状态跟踪证据前，不调整行为 105 的候选权重、持续时间或客户端
  鱼钩接近系数。
- 不把“更快上鱼”的玩法偏好混入协议兼容修复。

## Further Notes

- `[事实]` f19 的概率语义和 35 条样本区间来自 PR #375 的维护者复核。
- `[事实]` 本地原校准日志存在 14/11 明显早于 14/9 的静止自动上钩记录。
- `[推断]` 用户观察到的高频“动作后立即中鱼”主要由静止低概率路径与动作判定路径的
  概率差异造成，而不是服务端漏发行为 105。
