# 多钩钓组一次上多条鱼

Status: in-progress

## Problem Statement

海钓倒钓臂、三钩串钩这类多钩钓组，现实里一次抛投可以同时挂住几条鱼。当前服务端
虽然有完整的钩位模型（逐钩挂饵、逐钩判鱼、逐钩扣饵），但一杆只会派出一条鱼：
`rollFishForRig` 打乱钩位后取第一个成功的钩就返回，其余钩位在这杆里永远不参与判鱼。

玩家侧看到的现象是：六枚钩挂了六份饵，一次抛投仍然只上一条鱼，多钩只体现为
"换饵更勤"，没有体现为"一次能多上几条"。

## Solution

多钩钓组一次抛投可以同时挂住多条鱼：主鱼先咬，其余已挂饵的钩位各自独立掷骰，
满足总重预算的额外鱼同样下发鱼实体。玩家收竿时本杆所有鱼一次性结算，入护/放生
跟着玩家对主鱼的同一个选择走，不需要重新抛竿，也不会只到手一条。

额外鱼的数量与体量由三道闸门控制：钩位上限、总重预算、逐条降档。默认最多同时两条，
第二条起明显偏小，避免一杆挂上两条大物把钓组拉断。

## User Stories

1. 作为海钓玩家，我希望倒钓臂一次抛投能上两条鱼，以便多钩钓组和单钩有实际区别。
2. 作为玩家，我希望上来的第二条鱼明显比第一条小，而不是随机撞上两条大物。
3. 边界：总重超过预算时，多余的钩位直接不咬，而不是咬住后再断线。
4. 边界：收竿时本杆挂住的鱼一起上岸，不需要重新抛竿，也不会只到手一条。
5. 边界：额外鱼被客户端拒收时服务端直接放弃这一尾，不重推、不留下幽灵鱼。
6. 边界：服务重启后额外鱼丢失（它们是尚未结算的在途鱼），不产生错误渔获。

## Implementation Decisions

- `internal/gameserver`：`FishState` 增加 `Extra []*RolledFish`，表示本杆已咬钩、
  等待成为主战斗对象的额外鱼。**仅进程内，不持久化**；主鱼仍走原有 `Pending` 单值链路。
- 判鱼：`onBiteTimerTicket` 在主鱼判出并推送后，按剩余已挂饵钩位逐钩掷骰，
  经过总重预算与逐条降档过滤，逐条 `Push14_14`（`27.f23` 绑定各自钩 GUID）。
- 闸门参数（`tunables`，缺省即安全值）：
  - `multi_hook_bite`：总开关，默认 0（关闭，等价于旧行为）。
  - `multi_hook_max`：本杆最多鱼数（含主鱼），默认 2，上限按钩位收敛；实机本地服
    2026-11-13 调到 4（5 枚钩里 4 枚可用，第 5 枚是铁板拟饵自带三本钩，见下）。
  - `multi_hook_bite_chance`：每个额外钩位的独立咬口概率，默认 0.5。
  - `multi_hook_weight_budget`：总重预算系数 K，默认 0.55，预算 = K × 钓组最弱环。
  - `multi_hook_size_decay`：逐条降档系数 α，默认 0.6，第 i 条上限 × α^(i-1)。
  - `multi_hook_pull_budget`：总拉力预算系数 κ，默认 0.8，超过则按体重占比等比压缩 f8。
  - `multi_hook_hook_mount`：额外鱼的钩是否补挂竿位（1024），默认 1。钩缺这个运行位时
    客户端钩实体不进搏鱼态，鱼模型不会挂到那枚钩上。
- 协议：不新增命令、不改响应形状。多条鱼各自一条 14/14；14/11、14/12 按鱼 GUID 匹配
  （14/12 已有该匹配，14/11 新增解析）；`4/22` 仍按选中钩推送。
- 结算：`14/4` 结算主鱼的同时，把 `Extra` 里其余已咬钩的鱼逐条走同一个结算事务
  （`settleCatchXPWithQualifications`，各自一条 catch_log 与经验/银币），结算成功的
  移入 `FishState.Batch`；本杆能否继续不由服务端决定，见下。
- 入护/放生：`14/5` 入护主鱼后，`Batch` 里的鱼按同一次选择逐条入护（沿用
  `KeepFishingCatchWithCapacity`，护网满额即停），并逐条推 `4/22` 增量；
  `14/6` 放生则把 `Batch` 一并清空。
- 主鱼咬钩未刺中（`!hooked`）就收竿时，`Extra` 与 `Batch` 全部丢弃——本杆没有
  有效渔获，不能让 14/5 把在途鱼当成"入护"结掉。
- 兼容：关闭 `multi_hook_bite` 时所有路径与旧行为一致；不改数据库表与迁移。

## Testing Decisions

- 单元（纯逻辑）：总重预算与逐条降档的边界——预算不足时丢弃最重的、单条上限随序号衰减、
  α=1 且预算充足时退化为"每条都可上"。
- 单元（纯逻辑）：总拉力预算——Σf8 超预算时按体重占比压缩，压缩后 Σf8 落回预算内；
  未超预算时不动原始值。
- 单元（状态机）：`14/4` 后 `Extra` 清空、`Batch` 装载其余鱼、主鱼与额外鱼各一条
  catch_log；`14/5` 后护网条数等于本杆鱼数（`TestReelInSettlesWholeMultiHookCatch`）。
- 单元（状态机）：主鱼未刺中收竿时 `Extra`/`Batch` 都清空且不产生 catch_log
  （`TestReelInWithoutHookDropsExtras`）。
- 行为（实机一次）：倒钓臂两钩，看客户端是否连续两次接受 14/14（回 14/12 f0=6），
  以及入护后第二条是否继续搏斗。期望值来自日志中两条不同的 `fish=`/`hook=`。

## 钩位分配

多钩判鱼的前提是每条饵分到不同的钩位。分配规则：

1. `bait_hook:` 记录优先——组件数组删除后会紧缩，记录是原始钩位的可靠来源；
2. 记录缺失时按旧规则补算（`len(饵位) == len(钩位)` 才按序号配对），稀疏旧链不猜；
3. 单钩钓组：记录优先（拟饵自带的钩也保留），其余并到唯一钩位。

中间态纠正：装配是逐组件进行的，钩组件通常比饵晚装上。此时 `hookPositionsIn`
只看到模板声明的 1 个钩位（rig 50 模板只有 250），旧代码在
`rememberMountedBaitHook` 里把每条饵兜底绑到第一枚钩并持久化；钩装到 4 个之后
仍是 4 条记录全指向钩 0，多钩判鱼只看到 1 个有饵的钩位
（`logs/gameserver.log` 2026-11-13 07:17 `钩位=4 已挂饵钩位=1`）。

处理方式：

- `rememberMountedBaitHook` 配不到序号就不写记录，不再做单钩兜底；
- `baitHookAssignments` 检测"落在本钓组钩位上的记录只有一枚钩、而饵位序号跨越
  多个钩位"，判定为中间态，整批作废按序号重排，并把纠正结果回写数据库。

验证：`TestBaitHookAssignmentsPairByOrdinal`、
`TestBaitHookAssignmentsRepairsStaleSameHookMappings`；既有
`TestSelectedHookPartialNewMountAndSparseLegacyChain`（稀疏链不猜配对）与
`TestSelectedHookMappingKeepsEmbeddedLureHookInsteadOfSameOrdinalExternalHook`
（拟饵自带钩不被同序号外部钩替换）保持通过。

### 海钓钩位子槽（extra ≥ 1001）

`extra` 才是客户端的挂载位置，`ordinal` 只是组件数组下标；增删组件后数组会紧缩，
两者并不对齐。实机 2026-11-13 07:40 的装配就是反例：钩 `extra=250/1001/1005/1009`，
饵 `extra=300/325/326/1002/1003/1004/1006/1007/1008/1010/1011/1012`，
按 `ordinal` 配对把 4 个钩位塌成 1 组（`钩位=4 已挂饵钩位=1`）。

钩位命名空间来自客户端 `RigMarineBase`：钩位从 1001 起每 4 个索引一组
（1001/1005/1009），组内 1002/1003/1004 是挂在该钩位上的拟饵与珠子。分配改为：

- 饵 `extra ≥ 1001`：所属钩位 = `1001 + (extra-1001)/4*4`，直接归该钩位；
- 饵 `extra < 1001`（主线 300/325/326）：没有子槽结构，区分不了同一层上的多枚钩，
  继续走 `bait_hook:` 记录与既有补齐规则，不凭空占钩位；
- 子槽对应的钩位尚未装上时该饵不分配，等钩装上后下次读取自然归位。

只有当杆上存在 `extra ≥ 1001` 的钩组件、且所有钩位 `extra` 唯一时才启用该规则，
模板钩位（250/251/252）与旧数据保持原行为。

验证：`TestBaitHookAssignmentsFollowsMarineHookSubSlots`、
`TestBaitHookAssignmentsOverridesStaleRecordInSubSlotRig`；既有
`TestMarineArmHooksFormSeparateBaitGroups`、`TestMarineArmFourHooksAllKept`、
`TestMarineArmRebaitCoversAllHookOrdinals`、`TestMarineArmBreakOneHookKeepsOthers`
保持通过。

## Out of Scope

- 客户端同屏同时显示多条鱼、多鱼合力的力度条——由客户端决定，服务端只能约束参数。
- 额外鱼持久化与重启恢复（在途鱼，重启即丢）。
- 同杆多尾的经验/银币递减（如需平衡另开改动）。
- 三钩以上钓组的专门调参（机制支持，参数由闸门自然收敛）。

## Further Notes

- `[事实]` `hookPositionsIn` 取模板声明数与运行时钩组件的较大者；倒钓臂展开后实测
  250/1001/1005/1009 四条钩组件共存，`rig 59` 模板声明 250/251/252 三个钩位。
- `[事实]` `Push14_14` 的 `27.f23` 是钩 GUID，客户端用它把鱼实体挂到对应部件。
- `[事实]` 14/12 顶层是 `[竿 GUID, 鱼 GUID, 状态]`，服务端已按鱼 GUID 过滤不一致帧。
- `[推断]` 客户端能同时承载多条鱼实体：f23 绑钩 + 4/22 串钩嵌套容器说明模型按钩位组织；
  实机验证前不把它当作既成事实，故额外鱼按"可丢弃"设计。
- `[事实]` 断线由客户端判定并经 17/9 上报，服务端只在事后清终端件；因此多鱼的安全靠
  事前预算，而不是事后拦截。

## 收竿即终局：为什么不能"结算一条再接管下一条"

初版设计是收竿只结算主鱼，其余鱼留在队列里，等 `14/5` / `14/6` 处理完再把队首
提升成主战斗对象。实机证伪：

```
15:40:29  14/4 收竿（主鱼 ed_crab 入护），剩余=3
15:40:30  14/5 多钩接管下一条 fish=2e7d4253 → 重派 14/14 → 14/12 f0=3 hooked=true
15:40:31  14/1 抛投距离计算        ← 收竿后 1.2 秒客户端已经在算下一杆
15:40:36  14/1 抛投距离计算
15:40:43  14/2 实际抛投请求        ← 直接抛出去了
```

客户端把 `14/4` 当作"本杆结束"：它会立刻回到手持状态、开始下一次抛投。此时服务端
再派 `14/14`，客户端只回一条 `14/12`，既不画力度条也不把鱼模型挂到钩上。玩家看到
的就是"每次拉上来只有一条鱼"，队列里的鱼在下一次抛投被清空时消失。

所以多钩的"一次多条"只能在 `14/4` 这一次结算里完成：主鱼与其余鱼同批结算，
入护/放生跟着玩家对主鱼的同一个选择走。

`[事实]` 801 的结算体（813 `ndiejnnioni`）是单鱼结构，没有鱼列表字段；结算卡永远
只画一尾。其余鱼入护靠逐条 `4/22` 增量 + 一条系统播报告知玩家。

## Out of Scope（追加）

- 结算卡同屏列多尾鱼：客户端 801 结构不支持，需要改协议形状，不做。

## 钩上鱼模型：每枚钩都要自己的挂竿位

主鱼在 14/11 后由 `Push4_22Hook(true, gear)` 补挂竿位，但那条推送只取“线末端钩”
（`buildMountedHookTree` → `mountedHookGuid` 查 rig 槽位 12）。倒钓臂另外三枚钩从头到尾
没有挂过竿位，客户端把它们当静止件：`14/14` 的鱼实体进得了钓组（回 `14/12 f0=6`），
但钩不演，鱼模型也不挂，玩家在线快收完时只看得到主鱼一条。

`[事实]` 官方 9 次抓包：钩 `hgaijieklek` 中鱼时一律 20992|1024=22016；缺 1024 时
“客户端钩实体不进搏鱼态、浮漂无咬钩演出、左下角无搏鱼指示”（见
`specs/changes/hook-mounted-flag-all-rigs`）。

处理：`Push4_22HookGUID(hookGUID, mounted)` 按钩 GUID 单独推单钩 4/22（裸钩形状，
upsert 语义，不影响其它钩）。`pushExtraFish` 在派 `14/14` 之前先给它自己的钩挂位，
派完再补一次，避免实体创建把运行位重置。开关 `multi_hook_hook_mount` 默认 1。

验证：`TestBuildHookTreeByGUIDMarksOnlyItsOwnHook`（只改自己那枚）、
`TestPush4_22HookGUIDNoop`（空会话/空 GUID 不 panic）。

## 派发时机：额外鱼要等主鱼刺鱼确认后再派

补了逐钩挂竿位之后，实机 2026-11-13 16:38 仍然只看到一条鱼。日志把分歧点钉死了：

```
16:38:21.930  14/14 发鱼 fish=fc495b1d hook=ac05a6d7   ← 主鱼
16:38:21.935  14/14 发鱼 fish=fe084c14 hook=fb3b7f22   ← 额外（当时就派了）
16:38:21.937  14/12 额外鱼实体已就位 f0=6
16:38:21.942  14/14 发鱼 fish=aaaed036 hook=0657acbd   ← 额外
16:38:21.944  14/12 额外鱼实体已就位 f0=6
16:38:22.251  14/11 中鱼 fish=fc495b1d                 ← 只有主鱼被刺
```

客户端 `Fish` 状态机是 1(咬口) → 2(搏鱼) → 4(离场)。`14/14` 只把鱼实体放进钓组、
停在「等待玩家刺鱼」的咬口态；`14/12 f0=6` 就是这个态的回执。只有 `14/11` 之后
客户端才把鱼转进搏鱼态、按 `f23` 挂到那枚钩上。额外鱼从来没走过 `14/11`，所以
它们永远停在咬口态——钩不演、模型不挂。

处理（`multi_hook_push_on_strike`，默认 1）：

- 咬口阶段只派主鱼，额外鱼留在 `st.Extra` 里（`deferExtrasUntilStrike` 只记日志）；
- 主鱼 `14/11` / 海钓 `14/9` 刺鱼确认后调用 `pushExtrasAfterStrike`，延迟
  `multi_hook_push_delay_ms`（默认 350ms）再派额外鱼的 `14/14`——此时客户端已在
  搏鱼态，鱼实体应当直接挂到各自钩上；
- 补派被客户端拒收（`14/12 f0=3/5`）时不再"放弃该尾"，改为 `RolledFish.NoEntity`
  标记：不重派实体，但 `14/4` 照常结算——鱼确实咬了钩，只是画不出来。

验证：`TestExtrasDeferredUntilStrike`（咬口阶段队列不减少、刺鱼后收到 `14/14`、
鱼仍留队列等结算）、`TestRejectedExtraKeepsCatchWhenDeferred`。

## 实体渲染的实测结论：客户端每杆只画一条鱼

三次尝试与对应实证（2026-11-13）：

| 尝试 | 做法 | 客户端回执 | 结果 |
|---|---|---|---|
| 1 | 咬口时同时派 `14/14` | `14/12 f0=6` | 钩上只有主鱼 |
| 2 | 额外钩补挂竿位 1024，前后各推一次 `4/22` | `f0=6` | 同上 |
| 3 | 主鱼 `14/11` 刺鱼确认后再补派额外鱼 `14/14` | `f0=6 hooked=true`（三条全确认入组） | 同上 |

`[事实]` 三条鱼都拿到了实体入组回执，钩的挂竿位也已补齐，客户端仍只渲染一个鱼模型。
`[推断]` 客户端的搏鱼/模型挂载只维护一个"当前鱼"（刺鱼确认的那条），`14/14` 的
`f23` 只在它成为当前鱼时才用来选钩；服务端无法把额外鱼切成"搏鱼态"（14/15 只会
把鱼转成离场，不提供 1→2 的入口）。

因此"多钩可见"在客户端侧做不到，替代方案是逐钩文字清单：

- 刺鱼补派成功后推一条系统播报：`多钩：第2钩 绿青鳕 1.48 kg、第3钩 大西洋鲱 0.97 kg`；
- `14/5` 入护时再播一条带明细的汇总（结算卡只画一尾，801 的 813 是单鱼结构）。

鱼名取该水域的 `loc_wiki_fish.fish_zh` / `loc_fish.name_zh`，查不到就退回鱼种键。
开关仍保留：`multi_hook_push_on_strike` 置 0 退回"咬口即派"，`multi_hook_hook_mount`
置 0 退回"不补挂竿位"，便于客户端将来支持多模型时再验证。
