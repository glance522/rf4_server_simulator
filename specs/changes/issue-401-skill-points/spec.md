# 档案与技能树统一显示可用技能点

Status: done

## Problem Statement

玩家升级后首次打开技能面板，闲余点数显示累计获得的点数；再次加点后才显示余额，导致玩家误判可分配点数。关联 Issue #401。

## Solution

档案与技能树均显示等级所得点数加奖励、减去已投入点数后的余额。共享技能按同一身份扣除一次，余额不足时显示零。

## User Stories

1. 作为玩家，我希望升级、重连和加点后看到一致的可用点数。
2. 作为有奖励点数或共享技能的玩家，我希望奖励不遗漏、共享投入不重复扣除。
3. 边界：旧档的投入超过所得点数时，显示零而不是负数或无符号大数。

## Implementation Decisions

- 在 `internal/gameserver/skills_ops.go` 抽出接受已读取等级的余额计算，原有余额入口继续复用它；档案与技能树构造使用同一计算，避免重复读取档案。
- 修改 `BuildProfile307W` 的 f6 取值，统一 `BuildSkillTree311` 的自然余额计算；保留显式 override、字段类型、响应形状、数组与契约校验。
- `tools/proto.ps1` 的 3/1、3/20、5/1、5/2 查询确认响应类与标量类型；2/1、2/6 不在命令字典中，封装由现有推送调用点核对。
- 不改表、迁移、存档或加点事务。回滚实现即可恢复原下发口径。
- 客户端目标基线为 4.0.25034。本地实机结果为用户反馈，不等同于独立取得官方报文证据。

## Testing Decisions

- 复用 `sharedSkillTestServer` 的真实 SQLite 接缝，采用手算字面量，覆盖无投入、已投入、奖励、同类与跨类共享组、零余额和负余额钳制。
- 同时检查档案与技能树的余额、字段类型、对象形状，并覆盖升级前后余额和技能树显式 override。
- 更新旧档回归测试的档案期望为余额；保留共享节点原始记录不被读取路径修改的断言。
- 已完成红绿验证：新增测试在未修复基线上失败（共享组档案值 26、期望 21；已投入场景值 9、期望 6），应用修复后通过。

## Further Notes

- [事实] 修复前档案下发等级累计点数；技能树与余额入口扣除共享身份去重后的投入并计入奖励。修复后两个构造入口复用同一余额计算。
- [事实] 协议字典仅列出 f6 的类型和典型取值，没有独立确认其累计值或余额语义；证据标准见 `docs/agents/domain.md`。
- [推断] Issue #401 的客户端表现与用户本地回归支持 f6 表示余额，但不能替代官方客户端读取点或真实报文证据。
