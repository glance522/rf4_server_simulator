# 窝料系统与实例配方

Status: done

## Problem Statement

窝料需要按投放格子和时间影响鱼口，但此前只有静态商品档案，无法表达自制窝料、
PVA 棒和不同投放通道的真实用料。玩家制作出的同一 item_id 可能对应完全不同的
配方，若只按物品定义判定，所有自制窝料都会退化成同一个中性档案。

## Solution

服务端按玩家、钓点、5 米网格和批次记录投放账本，以在线游戏时间推进窝时；
投放时按剩余份数提高对口鱼种权重，并在过量时压低开口率。自制窝料和 PVA 棒
在制作时记录实际用料，投放时把用料冻结进账本，确保实例被消耗后窝效仍然稳定。

## User Stories

1. 作为玩家，我希望不同原料配出的窝料吸引不同食性鱼种，而不是所有自制窝料效果相同。
2. 作为玩家，我希望手抛、弹弓、食笼、PVA 和打窝器都能按各自实际消耗的份数记账。
3. 作为玩家，我希望窝料只在在线游戏时间内衰减，断线期间不扣窝时。
4. 边界：装填或挂饵拆出新物品实例时，实际用料必须随新实例保留。
5. 边界：同一请求重放不能重复扣料或重复投放。
6. 边界：窝料过量后开口率下降，并随窝时耗尽或鱼吃口逐步恢复。

## Implementation Decisions

- 模块：`internal/gameserver` 的钓鱼判定、制作、装配和动态协议处理。
- 命令：`12/1` 手抛窝料、`13/5` 弹弓抛饵；`13/5` 的 805 响应形状保持不变。
- 数据：新增 `groundbait_deposit`、`groundbait_clock`、`groundbait_recipe`
  三类玩家表，并登记到玩家存档表清单。
- 配方：制作时按实际扣除数量记录用料；装填或挂饵创建子实例时复制配方映射；
  投放时按实际消耗的子实例 GUID 读取并冻结到账本。
- 时间：会话 keepalive 持续推进在线窝料钟；业务路径也会补算，单次跨度封顶
  30 秒，避免离线时间被计入。
- PVA：水溶网只作为惰性载体，不参与食性；棒内干饵和添加剂按实际填充量计算。
- 兼容：客户端基线 4.0.25034；新迁移追加在现有迁移之后，旧库启动时自动升级；
  窝料总开关缺省关闭，关闭时不改变既有判鱼流程。

## Testing Decisions

- 单元：食性向量、专食性、掠食者冻结、窝料强度与过量曲线。
- 存储：真实 SQLite 上验证迁移、玩家表归属、投放幂等和过期批次清理。
- 协议/行为：手抛、弹弓、食笼/PVA、打窝器分别验证扣料、通道和落点记账。
- 实例链路：制作配方经过装填拆实例、挂饵拆实例后仍可读到相同用料；投放账本
  保存子实例用料。
- 时间：在线 keepalive 推进窝料钟，超过普通请求间隔时仍连续计时。
- 回滚后应失败的测试：实例配方继承、弹弓账本用料、PVA 实际填充量、在线计时。

## Out of Scope

- 不修改客户端原生饵团飞行动画；805 无落点和朝向字段。
- 不把静态目录中的窝料定义改成玩家可写数据。
- 不新增真实支付、运营或多人商业服务能力。

## Further Notes

- [事实] 客户端基线 4.0.25034 的真实请求已确认 12/1 与 13/5 的调用时机和扣料结果。
- [事实] 805 的协议字段只包含距离、散布、姿态、物品增量和移除信息。
- [推断] 鱼种权重与过量阈值为服务端玩法标定值，后续可通过 tunable 调整。
